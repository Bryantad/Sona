# Sona 0.15.5 Proof Mode Onboarding Plan

Status: architecture recorded before implementation; Phase 6 gates complete

This is Phase 6 of `Sona 0.15.5 — Trusted Developer Workflow`. It creates a
short, executable path from installation to privacy-conscious execution
evidence, Guardian policy, and one intentional denial. Release metadata remains
frozen at `0.15.4`.

## Current documentation architecture

The repository has accurate but separate user documents:

- `docs/QUICKSTART.md` installs the Python package and runs a first `.sona`
  program, but does not introduce Native Core, Proof Mode, receipts, or
  Guardian.
- `docs/guides/platform-installation-and-testing.md` defines the certified
  wheel and platform-specific Native archive matrix, including honest mobile
  and unsigned-macOS boundaries, but is a release-candidate verification guide
  rather than a first-use tutorial.
- `docs/guides/proof-mode.md` documents generation, verification, inspection,
  capabilities, receipts, and diagnostics in depth.
- `docs/guides/guardian.md` documents initialization, policy identity,
  capability decisions, drift, and recovery in depth.
- `docs/guides/proof-and-guardian.md` gives the complete release-trust workflow,
  including local attestation and advisory AI review.
- `README.md` and `docs/README.md` link those references individually, but
  there is no `docs/getting-started/` path joining their essential commands.

The onboarding gap is navigation and progressive disclosure, not missing core
behavior.

## Audited runtime behavior

The onboarding path is grounded in current source and tests:

1. The Python package installs `sona`; Native Core is distributed separately
   as a platform-specific archive containing `sona` or `sona.exe`.
2. `sona proof <program> --receipt <receipt>` delegates to
   `SONA_NATIVE_BINARY` or `sona-native` on `PATH`. Rust remains the sole
   producer; there is no Python execution fallback.
3. `sona proof inspect` and `sona proof verify` both use the shared Python
   schema-1 verifier. Their human views expose execution, runtime, Python and
   fallback status, capabilities, effects, and content identities.
4. `sona guardian init` creates a deterministic deny-by-default
   `sona.guard.json` only when one does not exist, then records a project-local
   baseline. It does not replace existing policy or complete state.
5. The default Guardian decisions are `deny` for filesystem read, filesystem
   write, and network.
6. A Guardian-bound Native run that requests filesystem write while policy
   denies it retains the Native capability diagnostic `SONA-FS-005`, exits
   nonzero, does not create the target file, and still publishes a structurally
   valid failed-execution receipt containing a denied `FS.WRITE` observation.
7. General Proof Mode verification validates that failed-execution receipt;
   `Receipt VALID` does not mean `Execution SUCCEEDED`.
8. `guardian check` and `guardian explain` are read-only. Explicit
   `--format text` makes tutorial output deterministic even when redirected.

## Content contract

Create `docs/getting-started/README.md` as the shortest supported trust
workflow:

1. install the Python package and matching Native Core;
2. create a dedicated practice project;
3. run a basic `.sona` program;
4. generate a standalone Proof Mode receipt;
5. inspect and verify the receipt;
6. initialize, check, and explain Guardian; and
7. run a Guardian-bound filesystem-write attempt that is intentionally denied.

The page will provide complete PowerShell and Bash/macOS/Linux command blocks.
It will use local files rather than repository-only examples and use an
explicit `SONA_NATIVE_BINARY` setup for extracted archives while also noting
the `sona-native` `PATH` option.

The first page will define Proof Mode as privacy-conscious execution evidence
about what Sona observed. It will use `execution evidence`, `integrity`,
`verification`, `observed effects`, and `capability evidence`. It will not call
a self-hashed receipt signed, authenticated, adversary-proof, or remotely
attested.

## Compatibility and scope constraints

- Use the product name `Proof Mode`; preserve the `sona proof` CLI namespace.
- Do not change receipt schema-1, canonicalization, runtime behavior, Sona
  syntax, Guardian policy, diagnostics, or release metadata.
- Do not introduce a new installer, package layout, or Native archive name.
- Do not hide the separate Native Core installation requirement.
- Explain that an intentional denied execution returns a nonzero exit code and
  that the resulting receipt can still pass integrity verification.
- Keep local attestation, advisory AI review, canonicalization details, and
  recovery mechanics in the deeper guides.
- Limit navigation changes to adding the onboarding entry and correcting
  nearby Proof Mode naming. README positioning is reserved for Phase 12.

## Implementation result

Phase 6 is complete without changing production runtime behavior, Proof Mode
schema-1, Guardian policy semantics, Sona syntax, or release metadata.

- `docs/getting-started/README.md` now provides one seven-step path from Python
  and Native Core installation through an ordinary run, Proof Mode generation,
  inspection, verification, Guardian initialization/check/explanation, and an
  intentional Guardian-bound filesystem-write denial.
- The page contains complete PowerShell and Bash/macOS/Linux setup and denial
  handling, including the expected nonzero exit code.
- Extracted Native archives use the implemented `SONA_NATIVE_BINARY` contract;
  an installed `sona-native` on `PATH` remains the no-configuration path.
- The denial walkthrough explicitly distinguishes receipt integrity from
  execution success and verifies that no denied target file is created.
- Trust language calls schema-1 privacy-conscious execution evidence and
  deterministic integrity checking. It explicitly excludes signatures,
  authenticated identity, remote/hardware attestation, and proof about
  unobserved external activity.
- `README.md`, `docs/README.md`, `docs/QUICKSTART.md`, and the Proof Mode guide
  link the onboarding path. Broader first-page positioning remains deferred to
  Phase 12.
- Nearby navigation and one touched README bullet now use the required
  `Proof Mode` branding rather than `Native Proof` branding.

## Executable documentation contract

`tests/onboarding/test_proof_mode_onboarding_0155.py` runs the documented
workflow with the real current Rust binary and Python CLI. It proves:

- ordinary compatibility execution succeeds;
- delegated Native Proof Mode execution succeeds with no fallback;
- inspect and verify expose the documented success facts;
- Guardian initializes with the default deny policy and reports Proof Mode
  ready;
- the Guardian-bound write attempt exits `1` with `SONA-FS-005`;
- `blocked.txt` is not created;
- the failed-execution receipt is structurally valid and Guardian-bound;
- the receipt records denied `FS.WRITE` with `PARTIAL` support;
- inspect and verify report `Receipt VALID` and `Execution FAILED`; and
- every local onboarding link resolves and every required command/trust phrase
  remains present.
