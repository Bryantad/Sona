# Sona 0.15.5 SPM hardening plan

Status: implemented and validated

## Scope

This phase hardens Sona's existing offline, local-path package manager. It does
not add downloads, archive extraction, a public registry, publishing, package
signatures, or a remote trust service.

The installation contract is:

```text
resolve local sources
        |
        v
validate manifest, names, paths, and source trees
        |
        v
copy into a project-local staging tree
        |
        v
verify staged integrity
        |
        v
atomically replace modules and lock state
        |
        v
remove rollback backup after both commits succeed
```

## Pre-change architecture

- `sona/spm.py` provides standalone `spm init`, `add`, `install`, `list`,
  `lock`, `verify`, and stdlib `catalog` commands.
- `sona pkg init` delegates only manifest initialization to SPM.
- `sona.json` schema 2 describes local file or directory dependencies and a
  configurable `.sona_modules` destination.
- `sona.lock.json` schema 1 records dependency path, version, integrity, and
  wall-clock timestamps.
- installation copies dependencies directly into the live modules tree,
  deleting an existing target before the replacement is known to be valid.
- `sona/lockfile_manager.py` is a separate whole-workspace release lock used by
  `sona lock`; it is not the SPM dependency lock and will not be merged or
  redesigned in this phase.
- no dedicated SPM test suite exists in the current checkout.

## Confirmed gaps

1. `spm.modulesDir` may be absolute or contain `..`, allowing writes and
   deletion outside the project root.
2. dependency names are split on dots without validation, so path separators
   or `..` can escape the modules directory.
3. local source symlinks and symlinks inside dependency trees are followed.
4. installation removes live package state before copying or verifying its
   replacement; a later failure leaves a partial installation.
5. dependencies are handled independently, so one bad dependency can coexist
   with already-mutated live state.
6. malformed manifests are reported with raw parser/host details and malformed
   lockfiles silently become empty lockfiles.
7. invalid dependency entries are silently skipped instead of rejected.
8. `installedAt` and `lockedAt` make equivalent locks differ across runs.
9. manifest and lock writes are direct, non-atomic writes.
10. the directory integrity stream lacks explicit record framing and has no
    algorithm identifier.
11. verification does not ensure that a hardened lock still corresponds to the
    current manifest dependency set.

## Compatibility decisions

### Local source boundary

Existing documentation intentionally supports sibling dependencies such as
`../my_pkg`. An explicitly configured local source may therefore be outside the
project root. This is not treated as an install destination.

The source must be a regular file or directory, cannot be a symlink, cannot
contain symlinks, and cannot contain the destination project. Absolute paths
remain accepted as explicit local inputs, while `spm add` stores a normalized
relative POSIX path where the platform permits it.

### Destination boundary

Every staging, backup, modules, package, and lock destination must remain under
the resolved project root. `modulesDir` must be a simple relative path with no
empty, dot, or parent segments. Existing symlink components are rejected.

Dependency names must be dotted Sona identifiers. Dots map to nested module
directories; slashes, backslashes, drive syntax, empty components, and parent
components are rejected.

### Lock compatibility

New locks use deterministic schema 2 with an explicit
`sha256-tree-v2` integrity algorithm and no timestamps. JSON object keys are
sorted and output uses LF line endings.

Verification retains read-only support for existing schema-1 locks using their
legacy integrity calculation. Installation and `spm lock` write schema 2 only.
Schema 2 also records whether development dependencies participated so the
manifest package set can be checked without guessing.

## Failure and recovery contract

- all dependencies are resolved, validated, and hashed before live state is
  changed;
- all package copies are written to a unique project-local staging directory;
- each staged package is hashed and compared with the resolved source and any
  declared manifest integrity;
- a complete deterministic lock is written to a no-clobber temporary file;
- existing modules and lock files are moved to unique rollback names;
- staged modules and lock files are atomically renamed into place;
- if either commit fails, new partial state is removed and both prior states are
  restored;
- successful completion removes staging and rollback paths; and
- failure messages identify the package or contract class without exposing raw
  operating-system exception text.

## Verification contract

`spm verify` checks:

- supported lock schema and integrity algorithm;
- valid lock package names and entry shapes;
- schema-2 manifest dependency-set agreement;
- installed target containment and symlink safety;
- package presence; and
- installed content integrity.

It remains read-only and does not regenerate the lock or repair packages.

## Proof Mode relationship

Schema-2 lock entries provide deterministic package content identities that a
future Proof Mode or build-provenance contract could reference. This phase does
not add package identity to schema-1 receipts, claim package authentication, or
create a signing/trust registry.

## Implementation order

1. add strict manifest, dependency-name, modules-path, source-tree, and lock
   validators;
2. add deterministic schema-2 integrity and atomic JSON writing while retaining
   schema-1 read verification;
3. replace in-place install with whole-set staging and verification;
4. add two-resource commit and rollback for modules plus lock;
5. test traversal, symlink, malformed-state, deterministic output, failure
   rollback, local sibling dependencies, and tamper detection;
6. update SPM documentation with exact local-only and trust limits; and
7. run focused/full Python, Ruff, metadata, and diff gates.

## Implementation result

`sona pkg` and `spm` now share the hardened local-only engine. Destination and
dependency traversal, source-tree symlinks, malformed manifests and locks, and
unsafe package names are rejected before live mutation. Installation stages
and verifies the complete package set before atomically replacing modules and
the deterministic schema-2 lock, with rollback on commit failure. Schema-1
locks remain read-only compatible. Focused validation passes with 23 tests;
3 Windows symlink cases are skipped where the host lacks symlink privilege.
