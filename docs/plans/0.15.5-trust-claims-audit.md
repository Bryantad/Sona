# Sona 0.15.5 Trust Claims Audit

Status: completed documentation audit

## Scope

The audit covered the root README, 0.15.4 release notes and implementation
report, Proof Mode specification and plans, Proof Mode and Guardian guides and
references, platform guidance, VS Code documentation, and trusted workflow
examples.

## Finding

The documentation already excluded signer identity, trusted timestamps,
hardware and operating-system integrity, remote attestation, Python/Native
parity, and AI-added trust. Several pages nevertheless described schema-1 as
"tamper-evident after creation," one verification page called a hashed field
"authenticated," and one combined guide called the local chain "strong" and a
stored receipt "immutable." Those phrases could be read as assurance against
an actor who can replace and re-hash local state.

## Canonical assurance language

Sona 0.15.5 uses this distinction:

| Assurance property | Status |
| --- | --- |
| Integrity | Available through canonical structure and self-hash consistency |
| Authentication | Not provided |
| Attestation | Not provided as a cryptographic, remote, hardware, OS, or trusted-runtime assurance |
| Trusted anchor | Not provided |

The `guardian proof attest` compatibility command records a local audit result;
its name and `attested` status do not change the assurance table.

## Changes made

- Replaced positive "tamper-evident" claims with "integrity-checkable" or
  "self-consistent."
- Replaced "authenticated field" with "hashed field."
- Replaced "immutable receipt" with "stored canonical receipt."
- Retitled the combined workflow table to distinguish what each step
  establishes from what it does not establish.
- Added the normative [assurance-level table](../spec/proof/assurance.md).
- Repeated that an actor able to replace a receipt can recompute its self-hash
  and that Guardian state is not a protected trust anchor.
- Preserved local-attestation command compatibility while defining it as a
  local audit record, not cryptographic attestation.

## Marketing boundary

Approved short language is "privacy-conscious, integrity-checkable local
execution evidence." Sona must not describe schema-1 as signed, authenticated,
tamper-proof, independently tamper-evident, remotely attested, hardware-backed,
or anchored by a trusted third party.
