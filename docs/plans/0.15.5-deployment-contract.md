# Sona Deployment Contract Investigation

Status: command deferred for Sona 0.15.5

## Decision

Sona 0.15.5 will not add `sona deploy`.

The repository has no existing deployment target abstraction, transport
contract, target-state query, rollback protocol, environment identity source,
or deployable artifact format. Adding a command now would give one filesystem
copy or vendor-specific script a misleading universal name. The bounded
[deployment evidence example](../../examples/trusted-workflows/deployment-evidence/README.md)
is the official reference workflow for this release.

## Required future contract

A future deployment command must define these before implementation:

| Concern | Required decision | 0.15.5 status |
| --- | --- | --- |
| Meaning of deploy | Exact desired state and success condition | Not specified beyond the local example |
| Supported target | Named local, container, host, or provider target | No general target selected |
| Transport | Filesystem, API, SSH, provider CLI, or another bounded mechanism | Local example uses instrumented filesystem copy only |
| Artifact | Immutable format and digest calculation | No deployable Sona artifact contract |
| Environment identity | Source of target identity and authentication | No authenticated source |
| Credentials | Acquisition, redaction, scope, and revocation | No deployment credential contract |
| Rollback | Previous-state capture, trigger, authority, and failure behavior | No deployment rollback protocol |
| Idempotency | Repeated-operation behavior | Not defined |
| Proof association | Which runtime-observed steps belong to one deployment | No deployment-level evidence schema |

## Intended future sequence

```text
resolve target and artifact
  -> validate policy, identity inputs, and prerequisites
  -> build and test
  -> stage immutable artifact
  -> perform bounded target operation
  -> verify target-observable result
  -> publish Proof Mode evidence
  -> retain rollback state and evidence association
```

Every stage must fail closed. A deployment must not be reported as successful
when receipt publication or required target verification fails.

## Proof Mode boundary

Schema-1 can currently identify the exact Sona program, Native Core engine,
capability decisions, instrumented effects, output bytes, and execution result.
It can record local filesystem effects used by the reference workflow.

It cannot currently establish:

- authenticated environment or host identity;
- cloud-provider acceptance or durable remote state;
- source-control provider identity;
- artifact authorship or signer identity;
- secret provenance;
- rollback availability or success;
- request-to-deployment causality; or
- remote attestation.

Application version, source revision, artifact digest, and environment label in
the reference example are declared metadata embedded in the preserved source.
The source hash binds those declarations to the executed program but does not
prove that they are true.

## Revisit gate

`sona deploy` may be reconsidered only after one target has a reviewed target,
transport, authentication, artifact, rollback, idempotency, error, and evidence
contract with end-to-end tests. That future design must not break Proof Mode
schema-1 or silently use Python fallback for a Native evidence claim.
