## Current architecture

### Existing provider abstraction

There are two overlapping provider surfaces. They must be understood before
0.16.0 adds another one.

1. `sona/providers/base.py` defines the older `AIProvider` abstraction. Its
   `infer(model, prompt, **params)` method is string-in/string-out and wraps a
   provider-specific `_raw_infer` call with policy checks, prompt denial,
   optional cache, circuit breaking, output enforcement, and performance
   logging. It has no typed task contract, lifecycle, streaming, cancellation,
   model identity object, or durable execution receipt.

2. `sona/developer_intelligence/contracts.py` defines the newer typed task
   surface. `TaskRequest`, `TaskConstraints`, `ProviderCapabilities`,
   `TaskPlan`, `TaskResult`, `ExecutionReceipt`, and related objects establish
   schema-versioned request/result data, preview-first behavior, limits, and
   redaction-aware serialization. This is the better compatibility boundary
   for 0.16.0 orchestration, but it is not yet a runtime lifecycle contract.

### Existing model registry and routing

- `sona/developer_intelligence/models.py` contains `ModelDescriptor` and
  `ModelRegistry`.
- Built-in descriptors include deterministic Sona analysis, Ollama Qwen 2.5
  Coder, disabled remote/provider placeholders, and a disabled legacy GPT-2
  entry.
- JSON manifests are schema-versioned, validate safe identifiers, and reject
  plaintext credential keys. Workspace and user model directories can override
  descriptors.
- `sona/developer_intelligence/routing.py` selects a compatible descriptor,
  applies locality/network/cost/policy checks, and records governance decisions.
- `sona/developer_intelligence/service.py` executes deterministic, Ollama,
  Hugging Face, or generic JSON HTTP providers and writes task receipts under
  `.sona/receipts/tasks`.

The registry currently describes models and provider configuration; it does not
own model lifecycle, local file integrity, hardware requirements, service
health, process supervision, or default-model persistence as required by
0.16.0.

### Existing local model support

- `sona/ai/local_models.py` discovers an Ollama endpoint, lists installed
  models, and optionally invokes `ollama pull`.
- `sona/ai/ollama_integration.py` provides the Ollama HTTP-backed completion
  adapter.
- `sona/ai/ai_backend.py` selects Ollama or legacy GPT-2 based on environment
  and availability. The term “local” currently means an Ollama or legacy
  backend; it is not a direct GGUF/llama.cpp execution path.
- `pyproject.toml` exposes optional Hugging Face/AI dependencies, but no
  `llama-cpp-python`, GGUF parser, or direct llama.cpp runtime dependency was
  found.

Therefore the objective’s initial direct GGUF → llama.cpp path is not present
and must be introduced behind a new explicit adapter contract. Existing Ollama
support should remain an optional adapter, not become an implicit fallback for
the direct local path.

### Existing resilience and queue-like helpers

- `sona/ai/retry.py` contains an in-memory circuit breaker and exponential
  backoff helper. It is feature-gated and has no durable retry record,
  workflow identity, recovery journal, or cancellation contract.
- `sona/ai/batcher.py` contains a feature-gated, process-local timer-based
  micro-batching queue. It uses `threading.Event`, has no bounded channel
  policy, durable item identity, typed messages, backpressure contract, or
  restart recovery.
- `sona/ai/cache.py` is an in-memory cache helper.
- `sona/interpreter.py` has in-memory trace, focus, working-memory, and
  cognitive metadata behavior. These are interpreter facilities, not a durable
  workflow runtime.

No general workflow engine, typed event bus, bounded channel abstraction,
durable task/step journal, supervised service registry, structured-concurrency
scope, or resource-budget controller was found.

### Existing policy, Guide, Proof, and Guardian boundaries

- `sona/developer_intelligence/governance.py`, `sona/policy.py`, and
  `sona/ai/capability.py` provide policy and capability checks for developer
  intelligence. They are advisory/governance surfaces, not native execution
  capability grants.
- `sona/guide` is deterministic and local. It remains the authority for
  compiler/runtime facts and must not be replaced by a model-generated answer.
- Native Proof Mode is implemented in the Rust Native Core and emits the frozen
  `sona.native-proof.schema-1` receipt contract. Its verifier, canonicalization,
  capability/effect vocabulary, and Guardian binding are already documented
  under `docs/spec/proof/`.
- Guardian remains a local resilience and trust-state facade. It owns project
  state, baselines, drift, recovery, and proof binding; it must not become an
  AI provider or a general workflow engine.
- The VS Code extension currently exposes Proof Mode Explorer and Sona AI
  Console surfaces. It does not yet expose a general local-runtime lifecycle,
  workflow, model service, or hardware panel.

These are separate authorities. A 0.16.0 model proposal may explain or
prepare work, but it cannot create or modify Proof evidence, approve its own
capabilities, alter Guardian state, or replace Guide facts.

## Missing pieces against the 0.16.0 plan

The following gaps are confirmed by repository inspection:

1. No general local intelligence interfaces exist for
   `LocalModelProvider`, `RuntimeAdapter`, `HardwareProfile`,
   `ContextManager`, or `InferenceQueue`.
2. No direct GGUF/llama.cpp provider or explicit model-file identity and
   integrity contract exists.
3. Model registry commands for add/list/inspect/remove/default are not a
   complete persistent local-model lifecycle.
4. Hardware inspection is not a first-class, typed, testable capability. The
   current descriptors do not express hardware requirements or observed
   hardware facts.
5. No persistent local model service with start/stop/status/health semantics
   exists.
6. The developer-intelligence service can produce deterministic proposals and
   provider results, but does not provide a complete Guide-backed proposal
   validation, preview, approval, and execution lifecycle.
7. Task receipts exist for developer-intelligence requests, but there is no
   durable workflow identity, step identity, append-only journal, replay/recovery
   model, or cancellation-safe publication contract.
8. No typed event/message system or bounded channel/backpressure contract
   exists.
9. No generalized supervised-service state machine, structured-concurrency
   scope, health transition model, or resource-budget enforcement layer exists.
10. Proof/Guardian capability boundaries are not yet generalized to all new
    runtime effects. Schema-1 compatibility must remain frozen while any new
    runtime evidence contract is designed separately.
11. CLI and VS Code runtime UX for local model lifecycle, hardware, service
    health, and workflow recovery is not present.
12. The repository does not yet contain the four 0.16.0 end-to-end examples or
    a complete cross-platform release gate for the new runtime.

## Proposed architecture and decisions

### New boundaries

The implementation should introduce small, separately testable packages,
rather than extend the legacy AI backend or interpreter directly:

- `sona/intelligence/`: model metadata, local provider contract, runtime
  adapter contract, hardware profile, context policy, inference queue, and
  provider lifecycle.
- `sona/workflow/`: task/step identities, typed events, bounded channels,
  journal records, state transitions, cancellation, retry, and recovery.
- `sona/runtime/`: supervised service lifecycle, health, resource budgets,
  capability mediation, and execution coordination.

The final package names may be adjusted to match existing project style, but
the ownership boundaries should remain. The initial APIs should be defined
before adding Sona syntax or UI commands.

### Authority and trust rules

1. Guide remains authoritative for language/compiler/runtime facts.
2. Proof schema-1 remains frozen and is not extended for 0.16.0 workflow data.
3. Guardian remains responsible for local project trust state and proof
   binding; it is not redesigned as the workflow engine.
4. Model output is untrusted proposal data until it passes deterministic
   validation and explicit policy/capability approval.
5. Local inference is explicit. A missing local runtime must produce a clear
   unavailable result; it must not silently fall back to a remote provider.
6. Registry metadata describes identity and configuration. Runtime adapters
   own loading/execution. The registry must not directly manage processes.
7. Receipts and journals must be redaction-safe and versioned. Secret values,
   raw prompts, credentials, and unrestricted environment data are not durable
   by default.
8. New abstractions must be generic to Sona’s local runtime. Do not copy
   PersaCom-only kernel/device primitives into this repository without a Sona
   requirement and contract.

### Compatibility

- Existing `sona.developer_intelligence` providers and task contracts remain
  usable during migration.
- Ollama remains an optional adapter.
- Existing Proof and Guardian commands retain their current behavior.
- No Sona syntax change is required for the initial 0.16.0 phases.
- New workflow/model/runtime records need their own schema versions and must
  not be placed inside the frozen Native Proof schema-1 payload.

## Recommended implementation order

1. Freeze this inventory and baseline; add contract tests only where they
   describe existing behavior.
2. Define the local-intelligence interfaces and model identity contract.
3. Implement hardware inspection as observation first, with deterministic
   serialization and no implicit enforcement.
4. Add the direct GGUF/llama.cpp adapter behind an explicit local provider,
   including capability reporting and no-fallback behavior.
5. Extend the model registry and CLI with persistent, validated model records.
6. Add a local model service lifecycle and health/status contract.
7. Add deterministic Guide-backed proposal validation, preview, approval, and
   explicit execution handoff.
8. Define workflow/task/step IDs, durable records, journal publication, and
   cancellation/recovery semantics.
9. Add typed events, bounded channels, backpressure, supervised services,
   resource budgets, and structured concurrency in that order.
10. Generalize capability/effect mediation and connect the resulting runtime
    evidence to existing Proof/Guardian boundaries without changing schema-1.
11. Add CLI and VS Code runtime UX after the headless contracts are stable.
12. Add the four examples and complete Windows, Linux, macOS, and package
    release gates before changing the final version metadata.

## Risks and open decisions

- The supported llama.cpp integration strategy is not selected yet. The
  project must decide whether the first adapter is an optional Python package,
  a bundled native helper, or a process boundary, while preserving offline
  and platform-specific installation behavior.
- GGUF metadata and model-file hashing need a stable, bounded contract before
  model identity can be trusted.
- Hardware inspection must distinguish observed facts from policy decisions;
  it must not imply that a reported device is secure or available for every
  runtime.
- Journal durability, atomic publication, replay, and cancellation ordering
  need explicit tests before workflows can claim recovery.
- Concurrency and backpressure behavior must remain deterministic enough for
  tests while still supporting real local inference.
- The existing local Windows gates do not certify Linux or macOS. Hosted or
  native platform runs remain required for cross-platform release claims.
- The current system Node is `v24.19.0`, while the repository pins Node
  `20.19.5`; extension gates should continue to use the pinned toolchain.

## Phase 0 conclusion

The repository has useful provider, model-registry, governance, task-receipt,
Proof, Guardian, Guide, and VS Code foundations, but it does not yet have the
general trusted local runtime described by 0.16.0. The safe next step is to
define and test the new headless contracts, starting with local intelligence
and model identity. That Phase 0 condition has been met; Phase 1 work is tracked
below. No version metadata has been changed.

The first API-first contract slice is implemented on branch
`codex/0.16.0-trusted-runtime`:

- `sona/intelligence/contracts.py` defines GGUF model identity, observed
  hardware facts, bounded inference context, request/response/chunk records,
  explicit model and inference lifecycle vocabularies, residency policy, and
  protocols for local providers, runtime adapters, context selection, and
  inference queues.
- `sona/workflow/contracts.py` defines UUID-backed workflow/task/step IDs,

## Phase 2 model registry API

The core registry API is implemented in `sona/intelligence/registry.py` as
`LocalModelRegistry`. It provides registration, listing, inspection, removal,
and default selection. It validates the registry schema and fields, accepts
only regular files with a GGUF header, resolves model paths, optionally
verifies declared SHA-256 values, and publishes canonical JSON through
same-directory atomic replacement. Loading registry state never starts a
model. The older `sona.developer_intelligence.ModelRegistry` remains the
task-provider catalogue and is not the local artifact-of-record.

The registry API tests prove strict malformed-state rejection, duplicate and
missing-artifact rejection, GGUF magic validation, optional declared-hash
verification, canonical persistence, reopen/default behavior, removal, and
preservation of corrupt registry bytes. CLI commands and GGUF metadata
compatibility analysis remain future work; registration currently validates
the format header but does not load the model or assert runtime compatibility.

## Phase 3 direct local runtime slice

The optional direct runtime adapter is implemented in
`sona/intelligence/llama_cpp_runtime.py`. It discovers the Python llama.cpp
binding lazily, validates model identity and the GGUF header before loading,
checks an optional SHA-256, and calls the in-process llama.cpp API directly.
It does not use the legacy Ollama provider or a cloud route. CPU execution is
explicit; a requested CUDA path checks whether the installed binding reports
GPU-offload support and fails rather than silently falling back if it does
not. The optional dependency is pinned as `llama-cpp-python==0.3.35` under the
`llama-cpp` extra and is not added to the default install.

The adapter supports token streaming, serialized access to a loaded model,
provider/runtime identity in responses, and cancellation/deadline checks at
token-generation boundaries. These are cooperative checks: a native prompt
evaluation call can delay observation until it returns, so the adapter does
not claim hard real-time interruption. The tested environment has a CPU-only
Windows wheel; CUDA execution and Linux/macOS builds are not certified here.
The adapter currently invokes the model directly but does not yet provide the
resident service, queue lifecycle, hardware inventory, or CLI UX required by
later phases.

The offline integration test used a pre-staged 19 MB GGUF fixture with its
expected digest and replaced Python socket connection entry points with
fail-fast stubs. It completed direct CPU inference without a network
connection and without Ollama. This proves the tested invocation path only;

## Phase 4 persistent local inference service

`sona/intelligence/service.py` adds `LocalAIService` around the runtime
adapter. It owns one worker and one configured model, keeps that model loaded
for successive requests, serializes runtime access, and exposes bounded
submit/state/cancel/wait operations plus bounded-buffer streaming. The default
residency policy is `automatic`: after 300 idle seconds the service unloads
the model into `SLEEPING`, retaining its configured identity; the next request
reloads it directly through the same local adapter. `while_coding` can hold the
model resident while the host reports coding activity. `always_loaded` and
`manual` suppress idle eviction. Closing the service unloads the active model;
a transient unload failure is retried once by a later `close()` cleanup pass.

Enforced service budgets are the bounded pending-job count, single inference
concurrency, maximum configured model context, and maximum output tokens per
request. Queue overflow rejects the new job. Cancellation is cooperative, and
`close(timeout)` returns false rather than force-killing native code if the
runtime does not stop within the requested wait. RAM and accelerator-memory
limits are explicitly reported as `UNSUPPORTED`; this service is not an OS
sandbox and does not claim those limits are enforced. A model runtime failure
causes best-effort unload, records `ERROR`, and requires explicit model reload;
it never falls back to Ollama or a cloud provider. This service is resident
within one process, not a cross-process daemon or durable service supervisor.

The offline GGUF integration test now also issues two sequential inferences
through `LocalAIService` with Python socket connection hooks replaced by
fail-fast stubs. This demonstrates warm in-process reuse through the local
service; it does not prove whole-process or OS-level network isolation.

## Phase 5 Guide + local reasoning slice

`sona/guide/local_reasoning.py` adds an explicit second reasoning tier through
the `LocalModelProvider` contract. Callers must first obtain the deterministic
`GuideResponse`, then opt in to `explain_with_local_model`. The result keeps
that same deterministic object intact and adds a distinct
`unverified-local-advisory`; it is not a diagnostic, fix, compiler fact,
capability decision, Proof receipt, or Guardian decision. The Guide catalog
and existing Guide request/CLI transports remain deterministic and unchanged
unless a caller explicitly invokes the new API.

`GuideContextManager` currently supports reviewed catalog explanations only.
It excludes source paths, raw diagnostic messages, spans, fixes, and arbitrary
metadata. The only user-source content is an explicitly supplied selection,
limited to 8 KiB; complete context is limited to 16 KiB. Oversized input is
rejected rather than truncated. No workspace/file discovery is performed.
Provider and response identities are checked for explicit `local` execution,
and returned model text is size-limited and labeled unverified. There is no
automatic code edit, validation bypass, or remote fallback. CLI/editor UX,
concept/selection augmentation, and accepted-edit workflows remain later
work.

## Phase 7 Durable workflow journal and inert restore

`sona/workflow/persistence.py` adds `WorkflowJournalStore`. With a store
configured, `WorkflowLedger` writes the next journal record before returning an
accepted state transition and restores its prior in-memory record if
publication fails. Per-workflow records are canonical, version-1 UTF-8 JSON
snapshots in a sequential hash-chained event log. Staged record files are
flushed and atomically published without replacing an existing sequence; a
separate atomically replaced snapshot is a cache, not the source of truth.
Recovery validates canonical bytes, field sets, IDs, definition DAGs, retry
counts, timestamps, task/step/workflow state consistency, event sequence, and
the hash chain. Corrupt or incomplete published records fail closed.

`WorkflowLedger.restore()` is explicit and inert. A workflow last persisted
with a RUNNING or CANCELING step is loaded as BLOCKED with
`SONA-WORKFLOW-RECOVERY-REQUIRED`; no step operation runs. The caller must
explicitly choose `resume_step` to retry from the beginning or mark the step
failed; the declared retry maximum applies. Persisted operation names are
restricted to registered-style IDs so
arbitrary command text, paths, and prompts are not copied into the journal.
Limits cap workflow count, event count, record size, and aggregate store bytes.

Phase 7 does not yet persist a trusted execution-approval/capability decision,
perform a side effect, authorize recovery, provide cross-process writer
coordination, or claim tamper resistance against an actor who can rewrite local
files and recompute hashes. Directory-entry fsync is best-effort on Windows.
These limits are documented in
[`docs/spec/runtime/workflows.md`](../spec/runtime/workflows.md); the journal
is local integrity evidence, not signed provenance.

## Phase 8 Bounded retries, cancellation, and explicit recovery

`RetryPolicy` now validates finite delay values and caps maximum attempts at
1000. `WorkflowLedger.schedule_retry` moves an active step to `RETRYING`,
computes fixed or capped exponential delay, persists its UTC `retry_after_utc`,
and stops at the configured attempt budget. Exhaustion becomes terminal
failure. `release_due_retries` is an explicit poll; it does not sleep, spawn a
timer, or start the operation. A retry resumes only after its deadline and a
separate `start_step` call.

Interrupted `RUNNING`/`CANCELING` steps require the new explicit
`resume_step` decision: `RETRY_FROM_START` (only when an attempt remains) or
`MARK_FAILED`. Generic `unblock_step` and cancellation cannot bypass the
recovery-required state. The decision is recorded in allowlisted event detail.
Active cancellation still requires the owner to acknowledge that work has
stopped. Retrying/canceling work drops its retry deadline. New workflow
snapshots use schema 2 with `retry_after_utc`; schema-1 workflow snapshots and

## Phase 10 bounded channels and backpressure

`sona/runtime/channels.py` implements `BoundedChannel` for schema-validated
`MessageEnvelope` data. Capacity is required and capped at 65,536 items. The
FIFO uses a condition lock; `BLOCK` waits, `REJECT` raises `ChannelFullError`,
and `DROP_OLDEST` replaces exactly the oldest item while reporting its message
ID in `SendReceipt`. Each outgoing message is snapshotted through the bounded
JSON envelope and validated against the channel's `MessageSchema` before
enqueue.

Send and receive support finite timeout and `threading.Event` cancellation.
Timeout, cancellation, full, and closed cases have separate exception types.
Closing wakes waiters, refuses further sends, and allows accepted queued data
to drain before `receive()` returns `None`. The channel is in-process and
thread-safe, but not durable; it promises FIFO item order, not fairness among
blocked callers. Message delivery remains data only and grants no authority.
No Sona syntax, process supervision, or parent/child task lifecycle is added.

The behavioral contract is in
[`docs/spec/runtime/channels.md`](../spec/runtime/channels.md); regression
tests cover FIFO, capacity, all backpressure modes, blocked send/receive,
timeouts, cancellation, close/wakeup/drain, and schema rejection.

## Phase 11 supervised service lifecycle

`sona/runtime/services.py` adds an in-process `ServiceSupervisor`. Registered
synchronous service targets receive `ServiceContext`; they explicitly report
startup readiness and cooperatively observe cancellation. A service failure is
isolated to that target and may restart only within `RestartPolicy`'s finite
limit. Failure details are reduced to `SONA-SERVICE-FAILED`, not exception
text. A normal target return is a clean `STOPPED` outcome and does not trigger
restart. Manual start after `FAILED` is explicit and resets that run's budget.

Optional parent IDs form a registration-ordered tree. Children start only
after the parent reports `HEALTHY`. A parent failure deliberately does not
implicitly stop descendants or unrelated services; explicit cascade stop is
child-first. `stop()` requests cancellation and honors finite timeouts without
force-killing uncooperative code; `False` means the service may still be
running in `STOPPING`. Thread/process crash recovery, durable service state,
health probes/heartbeats, resource enforcement, and capability authorization
remain out of this slice. See
[`docs/spec/runtime/services.md`](../spec/runtime/services.md).

## Phase 12 health, heartbeats, and state-machine contracts

`sona/runtime/health.py` adds `HealthMonitor`, `HealthPolicy`, and immutable
snapshots. A health subject starts `UNKNOWN`; explicit reports select
`HEALTHY`, `DEGRADED`, `UNHEALTHY`, or `UNKNOWN`. Heartbeats refresh liveness
without promoting unknown or clearing explicitly reported degraded/unhealthy
states. Missing contact derives degraded/unhealthy at configured monotonic
thresholds, and a fresh heartbeat clears only staleness-derived degradation.
Safe diagnostic codes are accepted; raw messages are rejected. There is no
background checker: staleness is evaluated on snapshot.

`ServiceContext` now exposes heartbeat and health-report methods, and
`ServiceSnapshot` separates health from operational lifecycle. Stopped,
stopping, and failed services report health as `UNKNOWN`. Health never grants
authority or triggers an automatic restart.

`sona/runtime/state_machine.py` adds bounded state/transition definitions and
a thread-safe machine. Only explicit `(state, event)` transitions apply;
undefined transitions raise `InvalidStateTransition` without changing the
state or sequence. This API is not yet wired into service/workflow execution.
Full semantics and limitations are in
[`docs/spec/runtime/health-state-machines.md`](../spec/runtime/health-state-machines.md).

## Phase 13 structured effects, capabilities, and trust boundaries

`sona/runtime/contracts.py` extends the generic effect taxonomy while keeping

## Phase 14 structured concurrency and resource reporting

`BoundedTaskGroup` owns a fixed worker pool, caps queued-plus-running tasks,
and separately caps retained task records. Tasks receive cooperative
cancellation contexts, stable IDs, lifecycle snapshots, and fixed failure
codes. Group shutdown joins children by default; context-manager failure
requests child cancellation before re-raising. Running Python callables cannot
be forcibly preempted, and no per-task CPU/memory isolation is claimed.

`ResourceBudgetReporter` combines caller-supplied typed measurements with the
existing `ENFORCED` / `OBSERVED` / `UNSUPPORTED` declarations. Unsupported
limits have no threshold and cannot be reported as passing; observed readings
may exceed their declared limit without implying enforcement. The reporter
does not sample or enforce resources. The bounded task-group worker and
outstanding-task ceilings are actual runtime limits, but do not bound memory
or CPU use inside tasks.

Full contracts and limitations are in
[`docs/spec/runtime/tasks-resources.md`](../spec/runtime/tasks-resources.md).
