# Sona 0.15.5 Zero-Configuration Proof Mode Plan

Status: architecture recorded before implementation; Phase 5 gates complete

This is the Phase 5 slice of `Sona 0.15.5 — Trusted Developer Workflow`.
It makes the existing Native Proof producer accessible through the installed
Python-compatible `sona` command and makes verified evidence understandable
without requiring users to read canonical JSON.

Release metadata remains frozen at `0.15.4` for this implementation slice.

## Current architecture

Sona currently exposes two cooperating command surfaces:

1. The Rust Native Core executable owns Proof Mode generation in
   `native/crates/sona-cli/src/proof.rs`. Its command is
   `sona proof <program> --receipt <path>`. It executes exactly once in Native
   Core, records schema-1 evidence, seals canonical JSON, and publishes without
   overwriting an existing receipt.
2. The Python package installs the `sona` console command. Its `proof` parser
   currently accepts only `verify` and `inspect`; both use the shared verifier
   in `sona/proof.py`.
3. `sona.proof.verify_receipt` independently verifies canonical storage,
   receipt self-hash, schema and runtime identity, no-Python/no-fallback engine
   fields, capabilities, execution metadata, program identity, and ordered
   effects.
4. Guardian builds on the shared verifier for project binding. It does not own
   general Proof generation or verification semantics.

Release archives commonly expose the Native Core executable as `sona-native`
after installation, while the executable inside a native archive is named
`sona` or `sona.exe`. The Python package does not install or discover that
binary today. No production `SONA_NATIVE_*` executable override or equivalent
binary-discovery convention exists in the repository.

## Observed gaps

1. The documented first-run workflow requires users to know which of two
   executables owns each Proof operation.
2. `sona proof app.sona --receipt app.sproof` is rejected by the Python CLI even
   when `sona-native` is installed and usable.
3. The human verifier omits program identity, runtime version, execution
   outcome, explicit Python involvement, and output identities.
4. The human inspector omits integrity status, explicit Python/fallback facts,
   capability decisions, program hashes, and output hashes.
5. The Python `KNOWN_COMMANDS` direct-file guard does not list `proof`, making
   routing depend on whether a same-named filesystem entry exists.

The receipt producer, schema, canonicalization, verifier result, and Guardian
binding do not need redesign for this phase.

## Command ownership decision

The installed Python `sona` command will remain the user-facing coordinator:

```text
sona proof app.sona --receipt app.sproof
sona proof verify app.sproof
sona proof inspect app.sproof
```

- `verify` and `inspect` remain in-process Python operations backed by
  `sona.proof`.
- A target other than the reserved `verify` and `inspect` actions is forwarded
  unchanged to the Native Core `proof` command.
- The coordinator never runs the program through the Python interpreter and
  never substitutes Python-compatible or automatic fallback execution.
- Native stdout, stderr, and exit code remain attached to the parent process so
  program output and existing Native Proof diagnostics are preserved.
- Delegation uses an argument vector with `shell=False`; no command string is
  constructed.

This is orchestration only. Rust remains the sole schema-1 producer and Python
remains an independent verifier.

## Native executable discovery contract

Discovery is intentionally narrow and deterministic:

1. If `SONA_NATIVE_BINARY` is set, its expanded path must identify a regular
   file. That explicitly configured executable is used.
2. Otherwise, resolve only `sona-native` through the operating-system `PATH`.
3. Never resolve or launch a generic `sona` name from `PATH`, because that name
   normally identifies the Python console launcher and could recurse.
4. Never fall back to Python-compatible execution.

The environment override is an explicit executable-trust decision by the
caller. Sona validates only that the target is a regular file; executable
provenance, signatures, and operating-system trust are outside the current
Proof Mode claim.

If discovery fails, the coordinator returns a stable, redacted launch failure
that says Native Core is required, names the supported installation/override
paths, and does not expose raw operating-system exception text. The error is a
coordinator failure, not a schema-1 receipt diagnostic, because no Proof Mode
producer was invoked and no receipt exists to verify.

## Human evidence contract

Successful `verify` and `inspect` output will answer these questions directly:

- what source or source-backed container ran and its content identity;
- whether execution succeeded and which exit code was recorded;
- which Sona runtime version and Native Core engine produced the evidence;
- whether Python was required or embedded;
- whether fallback was used;
- which capabilities were granted or denied;
- which normalized effects were observed and with what outcome/support;
- which byte-count and SHA-256 identities describe stdout and stderr; and
- whether schema-1 structure, canonical storage, and self-hash integrity are
  valid.

Plain-language labels and outcomes appear before technical SHA-256 identities.
`--json` remains the existing machine-readable verifier result and does not
change shape in this phase.

## Compatibility constraints

- Do not alter `sona.native-proof.schema-1`, receipt canonicalization, or
  receipt self-hash behavior.
- Preserve the frozen 0.15.4 fixture and shared Rust/Python vectors.
- Preserve `sona proof verify`, `sona proof inspect`, and their `--json` forms.
- Preserve direct `sona-native proof` usage and Native run/proof stream parity.
- Pass all Native Proof options through unchanged, including capability,
  Guardian, engine, and summary flags.
- Do not add Python fallback, signatures, PKI, remote attestation, Native HTTP,
  LSP, SPM, syntax changes, or release-version changes.
- Do not rebuild the VSIX unless extension-package contents change.

## Implementation order

1. Add a small, independently testable Native-binary resolver and delegation
   helper in the Python CLI.
2. Route Python `sona proof <program> ...` before argparse's receipt-operation
   subparser while reserving `verify`, `inspect`, and help for Python.
3. Add `proof` to the direct-file command guard and clarify Proof help text.
4. Expand shared human renderers using only already-verified result fields.
5. Add unit tests for discovery priority, missing/invalid override behavior,
   no generic-`sona` recursion, argument-vector forwarding, and exit-code
   preservation.
6. Add a real Native round-trip through `python -m sona proof` and retain all
   schema compatibility gates.
7. Align the task guide, technical reference, and specification verification
   page with the implemented command and output contracts.
8. Run focused and full Python tests, scoped Ruff, Rust gates only if Rust
   changes, and `git diff --check`.

## Implementation result

Phase 5 is implemented without changing the schema-1 receipt, Native producer,
Sona syntax, or release metadata.

- `sona proof <program> --receipt <receipt>` now delegates to the standalone
  Rust producer through `SONA_NATIVE_BINARY` or `sona-native` on `PATH`.
- `sona proof verify`, `sona proof inspect`, and help remain Python-owned.
- Delegation passes a fixed argument vector with `shell=False`, inherits
  streams, returns the Native exit code, never searches for generic `sona`, and
  uses a re-entry guard against Python-launcher recursion.
- Missing, invalid, or unstartable Native Core fails before execution with a
  redacted `SonaProofLaunchError` and creates no receipt.
- Verification and inspection now expose execution outcome, program kind,
  runtime and engine, Python/fallback facts, Guardian state, capabilities,
  normalized effects, and program/output/receipt identities.
- The human output states that Python was not involved in the recorded
  execution; it does not imply that the separate verification command itself
  is Python-free.
- Existing `--json` results, direct `sona-native proof`, the frozen 0.15.4
  fixture, and shared canonical/effect vectors remain compatible.

## Remaining limits and risks

- The coordinated workflow is configuration-free only after the separately
  distributed Native Core is installed as `sona-native`; archive-local users
  must set `SONA_NATIVE_BINARY`.
- `SONA_NATIVE_BINARY` is an explicit caller trust decision. The coordinator
  validates a regular file but does not authenticate or sign the executable.
- Self-hashed schema-1 receipts remain local integrity-checkable evidence, not
  signer identity, trusted timestamping, machine attestation, or replay proof.
- Native HTTP, LSP, SPM expansion, signatures, PKI, remote services, and
  release-version changes remain outside this phase.
