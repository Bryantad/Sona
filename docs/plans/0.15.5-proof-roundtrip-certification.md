# Sona 0.15.5 Proof Round-Trip Certification

Status: audit recorded before implementation; certification gates complete

Release metadata remains frozen at `0.15.4` for this implementation slice.

## Objective

Certify that the real Rust Native Proof producer and the shared Python verifier
implement the same `sona.native-proof.schema-1` contract. This slice does not
change Sona syntax, redesign Guardian, or add signatures, PKI, remote
attestation, LSP, SPM, Native HTTP, or release-hygiene cleanup.

## Current producer architecture

The Native CLI owns Proof production in
`native/crates/sona-cli/src/proof.rs`:

1. `parse_invocation` accepts a `.sona` or `.sbc` target and a new receipt
   destination.
2. `prepare_program` reads exact source bytes for `.sona`. For `.sbc`, it
   validates the source-backed container with
   `decode_source_backed_payload`, retaining both the exact container bytes and
   exact decoded source bytes.
3. `execute_prepared` parses, lowers, recompiles, and executes through the
   Native VM with Proof observation enabled.
4. `build_receipt_for_program` records engine identity, capability grants,
   redacted ordered effects, program identity, output hashes and sizes, and the
   first runtime diagnostic identity when execution fails.
5. `seal_receipt` hashes the compact `serde_json` encoding before inserting
   `receipt_hash`. The current locked Rust configuration does not enable
   `serde_json`'s `preserve_order` feature, so object maps serialize in lexical
   key order.
6. `persist_receipt` writes the complete compact receipt followed by one LF and
   publishes without replacing an existing destination.

The source-backed SBC format is real and deterministic: `sona compile` calls
`encode_source_backed`, while Native Proof calls
`decode_source_backed_payload`. Schema-1 records `program.kind="sbc"`, a hash
and byte count for the container, and a separate hash and byte count for the
validated decoded source.

## Current verifier architecture

`sona/proof.py` independently implements schema-1 verification. It validates
the stored canonical bytes, recomputes the self-hash with `receipt_hash`
omitted, and then checks schema, runtime and engine identity, no-Python and
no-fallback claims, capability booleans, execution metadata, source/container
identity, and ordered redacted effects.

Guardian consumes this verifier and adds project-baseline and binding checks.
It does not define general Proof semantics.

## Existing evidence

The existing native release gates already establish these producer-side facts:

- Native `run` and Native `proof` expose the same stdout, stderr, exit result,
  runtime diagnostic identity, and capability behavior for covered programs.
- Native Proof emits source identity for `.sona`.
- Native Proof emits both container and decoded-source identity for `.sbc`.
- Native receipts are compact JSON with a self-hash over the unsigned receipt.
- Python is neither required nor embedded and fallback is false.

## Certification gaps

1. Real Native-generated receipts are not currently passed through
   `sona/proof.py`; producer tests and verifier tests are separate.
2. `.sbc` producer identity is tested, but no independent verifier certifies
   the resulting receipt.
3. Run/proof behavior parity is producer-tested, but the same test does not
   complete the producer-to-verifier chain.
4. Corruption tests use synthetic receipts and do not start from a real Native
   receipt.
5. Rust and Python have independent canonicalization assertions instead of a
   shared frozen vector corpus.
6. No committed 0.15.4 receipt fixture currently protects forward schema-1
   verification compatibility.

No producer/verifier field discrepancy was found during the audit. The
remaining risk is interoperability drift: the implementations agree by
inspection, but that agreement is not yet enforced by a cross-implementation
gate.

## Decisions for this slice

- Promote the existing native-binary pytest fixture to shared test
  infrastructure so release and Proof interoperability tests build one real
  `sona-cli` binary per test session.
- Add dedicated interoperability tests under `tests/proof/` for `.sona`, `.sbc`,
  execution behavior parity, real-receipt corruption, canonical storage, and
  0.15.4 compatibility.
- Treat a corruption mutation as an unsealed alteration to hashed
  receipt content. Every such mutation must fail self-hash verification.
  Re-sealing a changed source or output digest is not evidence that the digest
  describes reality; schema-1 is deliberately a self-hashed local receipt, not
  a signature or replay verifier.
- Keep canonical storage strict: exact compact canonical bytes and the same
  bytes plus one LF are accepted; key reordering, pretty printing, extra
  whitespace, or more than one trailing LF are rejected.
- Store shared unsigned receipts, exact canonical payload strings, expected
  SHA-256 labels, expected receipt hashes, and expected verifier outcomes in
  one vector corpus consumed by both Python and Rust tests.
- Add a static valid 0.15.4 schema-1 receipt fixture and require later
  schema-1 verifiers to continue accepting it. Incompatible field or
  canonicalization semantics require a new schema identifier.

## Implementation order

1. Share the existing native-binary test fixture without changing production
   behavior.
2. Add the vector corpus and make Python and Rust consume it.
3. Add real `.sona` producer-to-verifier and run/proof parity coverage.
4. Add real source-backed `.sbc` producer-to-verifier coverage.
5. Add real-receipt corruption and canonical-storage matrices.
6. Add and verify the 0.15.4 compatibility fixture.
7. Align specification documents with the enforced compatibility contract.
8. Run focused Python, Rust formatting/Clippy/tests, Native standalone, and
   whitespace gates, recording any environment-only blockers.

## Validation result

The implemented certification slice found no producer/verifier field or hash
discrepancy.

- Real Native `.sona` success and capability-denial receipts verified through
  `sona/proof.py` and preserved Native `run`/`proof` output, exit, diagnostic,
  and capability behavior.
- A real source-backed `.sbc` receipt verified with separate exact container
  and decoded-source identities.
- Nine isolated mutations of actual Native receipts failed self-hash
  verification, including source, container, execution, capability, effect,
  output, runtime, fallback, and receipt-hash changes.
- Exact canonical bytes and one trailing LF were accepted. Reordered keys,
  pretty printing, leading/trailing whitespace, and two trailing LFs were
  rejected.
- Rust and Python passed the same four schema-1 vectors: basic success, runtime
  failure, capability denial, and filesystem read.
- A receipt emitted by `Sona native 0.15.4` from `examples/hello.sona` is frozen
  as the backward-compatibility fixture.
