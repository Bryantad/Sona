# Sona 0.15.5 Proof and Guardian Architecture Plan

Release theme: Sona 0.15.5 - Trusted Developer Workflow

Status: Proof foundation implemented; Guardian policy-binding audit complete

## Proof foundation pre-change architecture

This section is the recorded audit snapshot from before the first 0.15.5
implementation slice. The implementation status is recorded below rather than
rewriting the evidence that guided that slice.

Native Proof generation is implemented in the native Rust CLI. The command
entrypoint is `native/crates/sona-cli/src/main.rs`, which dispatches `sona proof`
to `native/crates/sona-cli/src/proof.rs`. Proof generation currently accepts a
source or source-backed bytecode container, requires a caller-provided
`--receipt` destination, enforces the native engine boundary, and rejects
Python compatibility or auto fallback.

Receipt schema-1 is emitted by `native/crates/sona-cli/src/proof.rs` with
`schema_id = "sona.native-proof.schema-1"`, `schema = 1`, and
`receipt_type = "native_execution_proof"`. The generated receipt records Sona
version, Native Core engine identity, source/container identity, capability
booleans, execution status, output digests and byte counts, effect records, and
an optional Guardian binding.

Proof evidence capture lives in `native/crates/sona-vm/src/lib.rs` and
`native/crates/sona-vm/src/host.rs`. The VM tracks stdout/stderr SHA-256
incrementally and records host effects only when proof observation is explicitly
enabled. Filesystem target identities are HMAC-SHA256 fingerprints keyed per
execution; raw paths, raw source, stdin values, stdout/stderr bodies, and
environment values are not written to the receipt.

Receipt sealing currently computes `receipt_hash` as SHA-256 over compact JSON
bytes with the `receipt_hash` member omitted. The Rust implementation uses
`serde_json::to_vec` over constructed `serde_json::Value` objects. Because the
objects are constructed with `serde_json::Map`, the practical output is compact
and sorted, but the schema should explicitly own canonicalization rules so
verification does not depend on incidental map behavior.

Guardian integration is split. Native Core can bind a proof to a local Guardian
baseline with `--guardian-root`, reading only `.sona/guardian/baseline.json` and
`.sona/guardian/trusted_config.json`. Python Guardian verification lives in
`sona/stdlib/native_guardian.py` as `guardian_proof_verify`,
`guardian_proof_attest`, `guardian_proof_review`, and
`guardian_proof_history`. The public CLI exposes these as
`sona guardian proof verify|attest|review|history`.

General Proof verification does not exist yet. Today, receipt verification is
available only as part of Guardian-bound proof verification, and therefore
requires an initialized Guardian baseline even for checks that are independent
of Guardian.

## Proof foundation gaps recorded before implementation

1. `sona proof verify <receipt>` and `sona proof inspect <receipt>` are missing
   from the Python CLI.
2. General receipt verification is not factored into a reusable module. Guardian
   has its own embedded verification checks, but those checks mix schema
   validation with Guardian baseline checks.
3. Schema-1 field requirements are documented in guides and reference prose but
   not as a dedicated spec tree under `docs/spec/proof/`.
4. Canonical JSON rules need a single Python implementation for verification
   and tests. The verifier should accept existing 0.15.4 receipts that are
   compact canonical JSON with an optional trailing newline.
5. General proof verification needs Sona diagnostics that fail safely without
   leaking raw paths, source text, stdout/stderr bodies, stdin values, or raw OS
   error text.
6. Capability and effect record validation should be explicit and independent
   of Guardian.
7. Fallback rejection should be an explicit general Proof rule:
   `engine.fallback_used` must be `false`, `python_required` must be `false`,
   and `python_embedded` must be `false`.
8. Guardian currently has `init`, `verify`, and a compatibility `check`
   function, but the canonical CLI exposes `verify`, not `check`, and there is
   no `guardian explain` command. 0.15.5 should add command contracts without
   redesigning Guardian internals.

## Recorded Proof foundation implementation order

1. Add a small Python verification module for Native Proof schema-1 receipts.
   It should load raw bytes, parse JSON, enforce canonical form, validate
   `receipt_hash`, validate required fields, and produce structured facts.
2. Add `sona proof verify <receipt>` and `sona proof inspect <receipt>` to the
   Python CLI. Verification should return a polished human summary by default
   and support JSON output for tests and automation.
3. Refactor Guardian proof verification to call the shared verifier for general
   schema/integrity checks, then keep Guardian-specific baseline binding checks
   local to `native_guardian.py`.
4. Add `docs/spec/proof/` with schema, canonicalization, effects,
   compatibility, verification, and threat-model documents aligned to the new
   verifier.
5. Add focused tests under `tests/proof/` covering valid receipts, corruption,
   invalid schema, missing fields, hash mismatch, capability/effect validation,
   no-Python proof identity, and fallback rejection.
6. Add or expose Guardian `check` and `explain` workflow contracts without
   changing Guardian policy semantics.

## Non-goals for this foundation pass

This pass must not add remote attestation, signatures, PKI, cloud verification,
new Sona syntax, LSP work, SPM work, or Native HTTP support.

## Guardian policy-binding audit

This section records the second 0.15.5 architecture slice before Guardian
behavior changes.

### Existing Guardian workflow

Guardian project configuration is `sona.guard.json`. Before this slice it
contains operational recovery settings (`validation_commands`,
`auto_recover`, and `excludes`) but no Native Core capability policy.
`guardian init` copies those settings into
`.sona/guardian/trusted_config.json`, creates a project inventory snapshot,
and writes `.sona/guardian/baseline.json`. Re-running `init` silently replaces
trusted state.

`guardian verify` and its `guardian check` compatibility alias compare the
current inventory and configuration hash with the trusted baseline. They are
read-only. `guardian explain` summarizes drift and names the intended workflow,
but it does not yet expose normalized policy decisions or a stable policy
identity. Some failure paths surface raw exception text and absolute paths.

Native Core's `--guardian-root` Proof Mode path reads the baseline and trusted
configuration directly in Rust, confirms that the program is baseline-tracked,
and adds a `sona.guardian-proof-binding.schema-1` object to the receipt. The
binding currently identifies the baseline and trusted configuration, but it
does not constrain the CLI capability flags used for execution.

### Missing pieces

1. There is no explicit, reviewable policy for Native Core filesystem or
   network capabilities.
2. There is no path-independent canonical Guardian policy identity.
3. `init` does not create a safe default configuration and may overwrite
   existing trusted state.
4. `check` and `explain` do not report capability decisions or Proof Mode
   readiness.
5. The Rust producer verifies the Guardian baseline but does not apply Guardian
   decisions to execution capabilities.
6. Guardian-bound receipt verification compares a fixed binding object and
   therefore needs an explicit legacy-extension rule before new binding fields
   are emitted.
7. CLI error handling can expose raw operating-system exceptions or paths.

### Minimal policy contract

The existing `sona.guard.json` format is extended rather than replaced. Old
configuration files remain valid. The normalized policy fields are:

```json
{
  "schema_version": 1,
  "capabilities": {
    "filesystem_read": "deny",
    "filesystem_write": "deny",
    "network": "deny"
  }
}
```

Each decision is exactly `allow` or `deny`. Missing capability fields are
`deny`; unknown capability names and unsupported decisions fail closed.
`console`, `process`, and `environment` are not configurable in this slice:
console remains required for Native Core program output, while process and
environment remain unavailable. Existing recovery fields retain their current
semantics and are not part of the capability-policy identity.

The policy identity is:

`sha256:` plus SHA-256 of the UTF-8 bytes of compact, recursively key-sorted
JSON for the normalized object above. It deliberately excludes project paths,
timestamps, validation command paths, exclusions, and other machine-specific
or operational values.

Normalized human and machine-readable decisions use these names:

| Policy field | Decision capability | Native receipt field |
| --- | --- | --- |
| `filesystem_read` | `fs.read` | `filesystem_read` |
| `filesystem_write` | `fs.write` | `filesystem_write` |
| `network` | `network` | `network` |

### Runtime binding and compatibility

For newly initialized, policy-aware Guardian state, Native Core treats
`--allow-fs-read`, `--allow-fs-write`, and `--allow-network` as requests. The
effective grant is the intersection of the request and the trusted Guardian
decision. A denied request remains denied in the receipt capability record,
and an attempted operation produces the existing Native Core denial diagnostic
and effect evidence. Guardian does not invent a second execution engine or a
second effect recorder.

The core Proof Mode receipt remains `sona.native-proof.schema-1`. New
policy-aware receipts add `policy_sha256` and `policy_enforced` only inside the
existing optional `guardian` object. Existing 0.15.4 receipts and existing
Guardian bindings remain valid. Guardian verification requires the original
binding fields for every receipt; it validates the policy fields only when they
are present. A policy-aware local state rejects a receipt whose declared policy
identity does not match, while a legacy binding with no policy fields remains
accepted under the legacy baseline-only contract.

### Workflow contracts

- `sona guardian init` creates a default deny-by-default configuration only
  when `sona.guard.json` is absent, never replaces an existing configuration,
  and returns an idempotent result when complete trusted state already exists.
  Partial or inconsistent state fails safely instead of being overwritten.
- `sona guardian check` is read-only. It validates configuration syntax and
  policy identity, baseline/trusted-state coherence, drift, and whether Proof
  Mode can consume the trusted state. It never runs project code, accesses the
  network, or modifies project or Guardian state.
- `sona guardian explain` is read-only and returns the same normalized
  decisions with plain-language meaning, warnings, and a next command.
- Captured CLI output remains JSON for automation compatibility. Interactive
  terminals may render a compact text view of the same result.
- Public diagnostics expose stable Guardian diagnostic identifiers and safe
  messages. Raw paths, raw JSON parser text, permission details, and operating-
  system exception text are not part of the public contract.

### Guardian implementation order

1. Normalize and validate the extended configuration and derive its canonical
   policy identity.
2. Make initialization no-clobber and idempotent, with safe handling for
   malformed configuration, invalid roots, partial state, and permission
   failures.
3. Extend read-only `check` and `explain` results with policy identity,
   capability decisions, and Proof Mode readiness.
4. Apply policy decisions in the existing Native Core Proof Mode execution
   path and emit optional nested binding fields.
5. Keep Guardian receipt verification compatible with legacy baseline-only
   bindings while validating policy-aware bindings.
6. Add Python and Rust tests for the happy path, denial path, legacy path,
   malformed policy, hash mismatch, repeated initialization, and read-only
   guarantees.
7. Align user documentation with the implemented contract and run the complete
   release gates.

## Guardian policy-binding implementation result

The second slice implements the recorded contract without changing core Proof
Mode schema-1 or release-version metadata:

- `sona.guard.json` now supports normalized deny-by-default filesystem-read,
  filesystem-write, and network decisions.
- Python and Rust derive the same path-independent canonical policy identity.
- initialization creates a missing default configuration without clobbering,
  refuses partial state, and is an idempotent no-op for complete state.
- read-only check and explain results include policy identity, normalized
  decisions, warnings, and Proof Mode readiness.
- Native Core intersects capability requests with trusted Guardian decisions,
  records effective capabilities and existing VM effect evidence, and adds only
  optional policy fields to the existing nested Guardian binding.
- Guardian verification accepts legacy baseline-only bindings and validates
  policy-aware binding identities when present.
- public workflow failures use stable redacted Guardian diagnostics.
