# Sona 0.15.5 Trusted AI Automation Preparation

Status: implemented and validated

This is the Phase 4 slice of `Sona 0.15.5 — Trusted Developer Workflow`.
It prepares the existing evidence and advisory-review surfaces for accountable
automation without adding an agent framework or inventing semantic evidence.

## Current architecture

Sona currently has four related but distinct layers:

1. `sona ai task` runs the Python developer-intelligence service. It applies
   `.sona/governance.json` provider and task-capability decisions, routes to a
   deterministic or configured provider, and can write a redacted task record.
2. Guardian uses the separate project capability policy in `sona.guard.json`.
   For Guardian-bound Native execution, that policy constrains filesystem-read,
   filesystem-write, and network capability requests.
3. Native Proof Mode observes instrumented Native Core host boundaries and
   records runtime capabilities, execution identity, output identities, and
   low-level effects.
4. `sona guardian proof review` verifies a Guardian-bound Proof Mode receipt
   before sending a redacted packet to the developer-intelligence service. The
   review is advisory, writes no AI task receipt, and is outside verification
   and local attestation.

The VS Code AI Console is another provider-oriented preview surface. It does
not execute through Native Proof Mode and is not evidence that an agent action
occurred.

## Observed gap

The current Guardian review packet contains receipt identity, execution
success, Guardian binding, and local-attestation status. It omits already
verified program identity, runtime identity, capabilities, output identities,
and observed effects. An advisory reviewer therefore cannot explain the most
useful runtime-grounded facts even though the shared verifier has validated
them.

There is also no end-to-end runner that binds an AI request to a Native
execution. Python provider calls, proposed patches, and task records are not
Native host effects. No current runtime boundary can establish that a model
requested, selected, or caused a particular action.

## `AGENT.ACTION` decision

`AGENT.ACTION` is deferred and must not be added to the Proof Mode effect
vocabulary in this release slice.

Today it is a higher-level application concept, not a runtime-observable Native
operation. Adding it would merely restate model or orchestrator metadata and
would create false evidence. Real tool behavior is represented only by the
low-level effects that Native Core actually observes, such as `FS.READ`,
`FS.WRITE`, `STDOUT.WRITE`, and the current unavailable `NET.REQUEST` boundary.

A future agent-action association requires all of these before it can become a
reviewed evidence contract:

- a runner-owned action identifier, not model-authored text;
- a stable action-request identity created before execution;
- an explicit binding to one Proof Mode execution;
- a binding to the relevant ordered low-level effect range;
- an outcome derived from runtime facts rather than agent claims;
- retention of the low-level effects instead of replacing them;
- a separately reviewed schema or extension mechanism compatible with the
  frozen schema-1 receipt contract.

Until those conditions exist, Sona does not claim request-to-execution
causality or agent-action evidence.

## Minimal 0.15.5 contract

This phase will enrich the existing post-verification Guardian review packet
with facts already validated by the shared Proof Mode verifier:

- program kind and SHA-256 identity;
- Native Core and no-Python/no-fallback identity;
- granted capabilities;
- execution status and output identities;
- normalized observed effects with outcome and support status;
- an explicit observation boundary stating that `AGENT.ACTION` is not
  represented and AI-request causality is not established.

Provider input will omit effect target fingerprints as well as source, raw
paths, output bodies, stdin values, credentials, and environment values. The
packet remains canonical and identified by `review_input_hash`.

The deterministic reviewer may summarize only those supplied facts. It must
state that no agent action or causal link is established and that analysis
adds no trust.

## Compatibility constraints

- Do not alter `sona.native-proof.schema-1` receipt fields or canonicalization.
- Do not add `AGENT.ACTION` to the shared effect vector.
- Preserve the 0.15.4 fixture and schema-1 vectors.
- Add only backward-compatible fields to Guardian verification/review results.
- Continue to reuse `sona.proof.verify_receipt`; Guardian gains no independent
  receipt verifier.
- Keep AI review read-only and outside Proof verification and attestation.
- Keep provider networking disabled unless explicitly requested and permitted.
- Keep release metadata at `0.15.4`.

## Test plan

1. Verify Guardian exposes only shared-verifier runtime evidence.
2. Verify advisory input contains capabilities and normalized observed effects.
3. Verify effect targets and all raw values remain absent from provider input.
4. Verify the packet declares no `AGENT.ACTION` and no AI causal claim.
5. Verify deterministic review describes only observed identifiers and repeats
   the trust boundary.
6. Use a real Guardian-bound Native execution for the integration assertion.
7. Preserve invalid-receipt rejection before provider routing.
8. Preserve all Proof Mode compatibility vectors and fixtures.

## Implementation result

Phase 4 is implemented without changing Proof Mode receipt schema-1, the
effect registry, Sona syntax, Native execution, or release metadata.

- Guardian verification now publishes a `runtime_evidence` view selected from
  the shared Proof Mode verifier result.
- Guardian advisory review receives program/runtime identity, capabilities,
  output identities, and normalized effects in addition to its existing facts.
- Effect target fingerprints are retained for local Guardian verification but
  removed from provider input.
- The packet explicitly records `agent_action: not-represented` and
  `ai_request_causality: not-established`.
- The deterministic reviewer summarizes only supplied capabilities and effects
  and repeats that no agent-action or causal claim is established.
- `AGENT.ACTION` remains absent from the shared Proof Mode effect vocabulary.
