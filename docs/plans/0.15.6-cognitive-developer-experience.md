# Sona 0.15.6 — Cognitive Developer Experience

Status: implementation contract

Release theme: **Learn while you build.**

## Product thesis

Sona 0.15.6 makes the language adapt from teacher to tool. The compiler,
runtime, Guardian, and Proof Mode remain authoritative. A new deterministic
Sona Guide layer explains their structured output at the amount of detail the
developer selected.

The release does not require online AI, does not change Sona syntax, and does
not permit generated prose to reinterpret compiler or trust-chain facts.

```text
Parser / Runtime / Guardian / Proof Mode
                  |
         Canonical diagnostic or fact
                  |
              Sona Guide
          /          |          \
      Guided      Balanced      Expert
          \          |          /
              CLI / LSP / VS Code
```

## Repository findings

The 0.15.5 source already provides useful foundations:

- `sona/developer_intelligence/diagnostics.py` defines the canonical Python
  diagnostic shape and reserved identifiers.
- `sona/developer_intelligence/frontend.py` supplies one parser-backed
  diagnostic pipeline shared by CLI and LSP.
- `sona/lsp_server.py` publishes canonical diagnostics and implements bounded
  completion, hover, definition, and document symbols.
- `native/crates/sona-diagnostics` owns the Native Core diagnostic shape.
- Proof Mode and Guardian already expose structured, deterministic facts that
  can be rendered without an LLM.
- the extension already delegates Proof verification to the Sona CLI instead
  of reimplementing trust logic.
- `sona/developer_intelligence/cognitive.py` already means static cognitive-load
  analysis, while Sona also has cognitive language/runtime constructs,
  accessibility modules, and older optional AI components.
- the public `profile` stdlib module contains process-local accessibility
  presets. It is not a persisted developer-learning profile.

Because `cognitive` already has several meanings, the new deterministic product
layer will live under `sona/guide/`. This keeps Sona Guide distinct from
language semantics, optional AI, and accessibility presets.

## Non-negotiable boundaries

1. Canonical diagnostics and runtime facts remain unchanged by presentation
   mode.
2. Guided, Balanced, and Expert are guidance-density choices, not diagnoses.
3. A quick fix is offered only when a deterministic rule can identify an exact
   source edit.
4. Every edit is previewable before application.
5. Learning state is local, bounded, inspectable, resettable, and contains no
   source text, paths, output, credentials, or inferred medical state.
6. Focus Mode may prioritize or group diagnostics, but it must not delete them
   from machine-readable complete output.
7. Proof Mode and Guardian explanations describe verified fields only. They do
   not strengthen evidence or introduce new trust claims.
8. Existing 0.15.5 commands, receipt schema-1, and valid project state remain
   compatible.

## Package architecture

```text
sona/guide/
├── __init__.py
├── catalog.py          # versioned diagnostic and concept knowledge
├── models.py           # explanation, fix, relation, and profile contracts
├── explain.py          # deterministic diagnostic/fact explanation
├── fixes.py            # exact source-edit rules and safety validation
├── cascade.py          # root/cascade relationships and focus ordering
├── profile.py          # local guidance preferences and familiarity state
├── render.py           # Guided/Balanced/Expert text and JSON renderers
└── learning.py         # lesson metadata and progress, not execution semantics
```

The package consumes canonical objects. It must not import VS Code code, own a
second parser, execute a program, or call an AI provider.

### Core contracts

`GuideRequest` contains a canonical diagnostic or structured Proof/Guardian
fact, optional source context supplied by the caller, guidance mode,
explanation style, and diagnostic density.

`GuideResponse` contains stable identifiers, structured sections, related
concept identifiers, zero or more validated fix previews, and provenance
identifying the deterministic catalog/rule that produced it.

`SourceEdit` contains a document identity supplied by the caller, an exact
range, expected original text, replacement text, and rule identifier. Apply
must fail if the expected text no longer matches.

`DiagnosticRelation` identifies a primary diagnostic and likely secondary
diagnostics with a deterministic rule and confidence class. It is a
presentation relationship, not a compiler causality claim.

All contracts receive schema-versioned JSON representations for CLI/LSP/editor
parity tests.

## Official controls

### Guidance mode

- `guided`: what happened, why, where, safe next step, example, and concept.
- `balanced`: concise problem statement and the highest-confidence action.
- `expert`: stable diagnostic identifier, location, and compact message.

### Diagnostic density

- `focused`: one likely root issue plus a count of suppressed presentation
  items.
- `normal`: primary issues and useful non-cascade diagnostics.
- `complete`: every canonical diagnostic in original deterministic order.

### Explanation style

- `simple`: short plain-language explanation.
- `visual`: deterministic text diagrams when a catalog entry provides one.
- `technical`: precise compiler/runtime terminology.

### Quiet mode

Quiet mode shows execution blockers and severe correctness problems only. It
does not alter machine-readable diagnostics or permanently discard deferred
items.

These controls are orthogonal. They must not be encoded as ADHD, dyslexia,
autism, or other medical labels. Existing accessibility presets remain
supported but do not select a learning level automatically.

## Local learning profile

Project-local state may be stored at `.sona/learning.json`. The initial schema
contains only explicit preferences and concept familiarity:

```json
{
  "schema": 1,
  "guidance_mode": "guided",
  "diagnostic_density": "normal",
  "explanation_style": "simple",
  "quiet": false,
  "concepts": {
    "variables": "learning",
    "loops": "new"
  }
}
```

Allowed familiarity values are `new`, `learning`, and `comfortable`.
Scaffold decay is deterministic and bounded. The implementation may use an
explicit encounter counter internally, but it must not claim that frequency
proves ability, difficulty, or diagnosis. Users can inspect, edit, disable, or
reset this state.

## Delivery sequence

### Phase 0 — 0.15.5 stabilization gates

These fixes land before Sona Guide behavior:

1. Probe the resolved Native executable before Proof delegation.
2. Reject a Python CLI / Native Core version mismatch with a stable diagnostic
   and remediation showing the resolved executable source.
3. Define installation ownership and precedence for `sona.exe` and
   `sona-native.exe` on every supported platform.
4. Correct stale manifest migration metadata that recommends `fs.read_file`;
   the canonical Native API remains `fs.read_text`.
5. Add regression tests for explicit `SONA_NATIVE_BINARY`, PATH resolution,
   stale binaries, aliases, and redacted launch failures.

### Phase 1 — deterministic Sona Guide foundation (P0)

1. Add the `sona/guide` models, catalog, and renderers.
2. Seed a deliberately small catalog from existing stable diagnostics,
   including undefined names, missing delimiters, filesystem capability denial,
   Proof verification failure, and Guardian availability/drift.
3. Add `sona why <diagnostic-id>` with text and `--json` output.
4. Add Guided, Balanced, and Expert rendering while preserving one canonical
   diagnostic payload.
5. Add the first safe fix rules: closest in-scope identifier and the exact
   deprecated/canonical API migration supported by the manifest.
6. Require preview by default; expose application only through an explicit CLI
   or editor action with stale-text protection.

### Phase 2 — focus and cascade foundation (P0)

1. Define a small reviewed relation table for parser delimiter failures and
   downstream parse/name/scope noise.
2. Rank likely roots deterministically using diagnostic ID, source range, and
   reviewed relation rules.
3. Return grouped results without mutating or losing the complete canonical
   sequence.
4. Recompute after each applied edit.

### Phase 3 — local profiles and scaffold decay (P0)

1. Implement schema-1 learning profile validation and atomic local writes.
2. Add CLI commands to show, set, and reset guidance preferences.
3. Add bounded familiarity updates only after explicit learning actions or
   successful deterministic fixes; do not infer competence from failures.
4. Render progressively less scaffolding while always honoring an explicit
   mode selection.

### Phase 4 — LSP and VS Code integration (P1)

1. Add LSP code actions backed by Sona Guide fix rules.
2. Add Explain Diagnostic and Explain Selection commands backed by shared CLI
   or protocol JSON, not TypeScript knowledge duplication.
3. Add first-run Guided/Balanced/Expert setup without medical labels.
4. Add focused/normal/complete density and quiet-mode settings.
5. Enrich completion and hover from the same concept/catalog source.
6. Keep views keyboard navigable, theme aware, reduced-motion, and opt-in.

### Phase 5 — executable learning surface (P1)

1. Add `sona examples`, `sona examples run <name>`, and a versioned example
   manifest.
2. Run every official example and every documentation code sample designated
   executable in CI.
3. Add `sona learn` only after lessons have a real parser/runtime execution
   contract, deterministic checks, and local progress storage.
4. Start with variables, conditions, loops, functions, collections, modules,
   files, Guardian, and Proof Mode.

### Phase 6 — stretch work (P2)

Beginner REPL, syntax playground, execution visualization, function-flow
visualization, and error timelines are stretch work. They ship only if P0/P1
acceptance gates remain green and no trust or diagnostic contract is weakened.

## Acceptance tests

The release is not complete until all applicable gates pass:

- the complete pre-change test suite baseline is recorded;
- existing Proof Mode, Guardian, Native, LSP, SPM, and example tests remain
  green;
- the same canonical diagnostic renders correctly in all three modes;
- `sona why` has stable text and JSON contracts for every seeded entry;
- unknown diagnostic identifiers fail safely and suggest no invented meaning;
- quick-fix previews are deterministic and refuse stale or ambiguous edits;
- Focus Mode preserves complete output and identifies only reviewed cascades;
- corrupt or oversized learning profiles fail safely without source leakage;
- profile writes are atomic and confined to the selected project;
- CLI/LSP/VS Code parity tests prove one knowledge source;
- every official executable example runs in CI;
- Proof and Guardian guided summaries remain consistent with their structured
  machine output and assurance boundaries;
- Python CLI / Native Core mismatch tests cover older, newer, missing, and
  malformed version output;
- wheel, sdist, VSIX, and Native packaging checks pass; and
- Windows, Linux, and macOS release certification is recorded separately rather
  than inferred from artifact names.

## Flagship acceptance scenario

Given a program that references `quant` when `quantity` is the closest visible
binding, Sona must produce one canonical undefined-name diagnostic. Guided,
Balanced, and Expert presentations differ only in detail. A fix is offered only
when the symbol match is unambiguous, previews this exact edit, and refuses to
apply after the document changes:

```diff
- let total = price * quant
+ let total = price * quantity
```

## Explicitly deferred beyond 0.15.6

- BYOM and direct `llama.cpp` integration;
- Nemotron or generic local-model runtime integration;
- cloud Tutor services or subscriptions;
- an AI agent framework;
- Native HTTP expansion;
- remote telemetry for learning profiles;
- new major syntax; and
- AI-generated fixes or explanations in the verification path.

## Known risks

- Python and Native diagnostic shapes are similar but not identical. A shared
  presentation contract needs explicit adapters and parity fixtures.
- The current `SONA-RUNTIME-003` undefined-name diagnostic may not contain the
  visible-symbol set needed for a safe suggestion; source analysis must supply
  that context deterministically.
- Existing accessibility profile names and extension copy use medical labels.
  They must not be silently mapped to guidance modes.
- Existing optional AI/cognitive modules contain overlapping terminology and
  must remain outside the deterministic Sona Guide dependency graph.
- Cascade classification can hide useful information if rules are too broad;
  the initial table must be small, reviewed, and observable in complete mode.
- GitHub-hosted cross-platform certification for 0.15.5 was blocked by an
  account billing lock. That external gate must be restored before 0.15.6 can
  make new Linux or macOS compatibility claims.

## First implementation slice

The first code slice is deliberately narrow:

1. record the full-suite baseline;
2. implement and test Native CLI/runtime version probing and mismatch failure;
3. repair the `fs.read_file` migration replacement to `fs.read_text`;
4. add `sona/guide` contracts and five catalog entries;
5. implement `sona why` text/JSON output; and
6. add unit and CLI tests without changing default diagnostic rendering.

This slice establishes the architecture before Focus Mode, persisted learning,
editor fixes, lessons, or visualizations are added.
