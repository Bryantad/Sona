# Sona 0.15.5 Runtime Identity Review

Status: implemented and validated

## Current answer

Schema-1 already answers "what program executed?" with the exact source byte
count and SHA-256, plus the source-backed container identity for `.sbc` input.
It answers "what kind of runtime executed it?" with `sona_version`, engine name
`native`, `python_required: false`, `python_embedded: false`, and
`fallback_used: false`.

That identifies the runtime class and version, but not the exact Native CLI
binary. Source revision is recorded by external release reports, not by the
receipt. The current verifier correctly rejects Python or fallback engine
records but ignores unknown engine fields.

## Compatible extension decision

Preserve every required schema-1 field and every 0.15.4 compatibility vector.
New Native producers will add one optional `engine.runtime_identity` object:

```json
{
  "native_binary": {
    "bytes": 123,
    "sha256": "sha256:..."
  },
  "source_revision": "git:<40 lowercase hex>"
}
```

`native_binary` is required whenever the optional object is present. Native
Proof Mode will hash its running executable before program execution and fail
closed if that identity cannot be read. `source_revision` is included only
when the build supplies a valid full `SONA_SOURCE_COMMIT`; development builds
may omit it.

The Python verifier will accept legacy receipts with no extension, validate
every supplied extension field, and expose only validated values. The human
inspector and VS Code Proof Mode Explorer will display the exact binary
identity and optional source revision.

## Assurance boundary

These fields improve correlation: a reviewer can compare the binary digest to
a separately published artifact digest and compare the revision to release
records. They remain self-declared fields inside a self-hashed receipt. They do
not authenticate the binary, source host, build system, Git provider, runtime
host, or operator and do not add a trusted anchor or remote attestation.

## Validation plan

- retain the frozen 0.15.4 receipt and shared canonical vectors unchanged;
- test legacy engine normalization without runtime identity;
- test valid and malformed optional runtime identities;
- build Native Core with a fixed 40-hex source revision;
- assert the receipt binary hash equals the executable's bytes;
- assert inspection and the VS Code model expose the validated identity; and
- verify Guardian advisory packets inherit only the shared verifier result.

## Implementation result

The compatible extension is implemented. Production Proof Mode hashes its
running Native executable before program execution and adds the optional full
build revision when `SONA_SOURCE_COMMIT` is valid. Release build tooling now
passes the source commit into Cargo. The shared Python verifier validates and
normalizes the extension, terminal inspection displays it, Guardian inherits
the shared verified engine object, and the VS Code Proof Mode Explorer displays
the executable identity and optional revision without reimplementing trust.

Validation completed with:

- 18 `sona-cli` Rust tests;
- strict `cargo clippy -D warnings`;
- 30 focused verifier and trust-claims tests;
- 11 real Native/Python round-trip tests;
- unchanged schema-1 vectors and a still-valid frozen 0.15.4 receipt;
- a real receipt whose recorded executable digest exactly matched the running
  Native binary; and
- successful VS Code compile and smoke tests for the extended shared-verifier
  model.
