# Sona 0.15.5 VS Code Proof Mode Explorer plan

Status: implemented and validated

## Objective

Add the smallest useful Proof Mode experience to the existing VS Code
extension without redesigning the extension or implementing receipt trust
semantics in TypeScript.

The trust boundary remains:

```text
VS Code commands and tree UI
        |
        v
installed Sona CLI
        |
        v
shared Python Proof Mode verifier
        |
        v
normalized JSON display model
```

The extension may validate that CLI output has the fields needed for display.
It must not canonicalize receipt JSON, recompute hashes, reinterpret schema
rules, or mark a receipt verified independently of the shared verifier.

## Pre-change architecture

- `src/extension.ts` activates the existing Sona command integration, AI
  Console, and Python language client.
- `src/sonaCliIntegration.ts` owns a shell-free Python subprocess transport,
  output channel, status item, and existing CLI-backed commands.
- `src/lspClient.ts` separately resolves the configured Python interpreter and
  starts `python -m sona.lsp_server --stdio`.
- the Sona activity container currently contains only the AI Console webview.
- the extension contributes no Proof Mode commands, receipt view, or receipt
  file association.
- `sona proof verify <receipt> --json` and `sona proof inspect <receipt> --json`
  return the shared verifier's normalized object. Invalid receipts return a
  structured Proof diagnostic and a nonzero status.
- `sona guardian proof review --project-root <root> --receipt <receipt>` is the
  existing receipt-aware Guardian explanation path and defaults to the local
  governed reviewer unless a provider is explicitly configured.

The pre-change TypeScript/esbuild compile and AI Console smoke test pass. The
pinned Node 20.19.5 dependency audit reports zero vulnerabilities.

## Gaps

1. developers must leave VS Code or use a terminal for every Proof Mode action;
2. verified receipt facts are not visible in the Sona activity container;
3. there is no direct route from an active `.sona` file to a requested receipt;
4. the CLI and LSP interpreter-resolution rules are duplicated and differ;
5. ordinary extension CLI launches prepend the workspace to `PYTHONPATH`,
   increasing package-shadowing risk for trusted workflow commands;
6. no extension smoke test protects the Proof Mode trust boundary or command
   contributions.

## Minimal support contract

The explorer displays:

- program and receipt names;
- execution success/failure and exit code;
- verifier status;
- Native Core identity, Python involvement, and fallback status;
- explicit capabilities;
- observed-effect identifiers, outcomes, support status, and counts;
- Guardian binding state; and
- redacted program, output, and receipt identities already returned by the
  shared verifier.

The explorer provides:

- **Run with Proof Mode** for a saved active `.sona` file;
- **Verify Receipt**;
- **Inspect Receipt**;
- **Open Receipt**;
- **Refresh Receipt**; and
- **Explain with Guardian** through the existing receipt review command.

Generation calls the existing `sona proof` namespace and requests a new receipt
path from the user. Verification and inspection always call the shared CLI
verifier. The extension does not silently overwrite a receipt.

## Security and privacy decisions

- subprocesses remain shell-free and receive argument arrays;
- Python is invoked with safe-path mode (`-P`) and the workspace is not added to
  `PYTHONPATH`, reducing project package shadowing;
- program execution and Guardian review require a trusted VS Code workspace;
- verification and inspection are read-only and consume verifier-normalized
  output;
- notifications use concise messages while detailed CLI diagnostics remain in
  the user-controlled Sona output channel;
- the extension does not read receipt contents to establish validity;
- no receipt path or receipt state is persisted across sessions; and
- no network permission is enabled for Guardian review by the extension.

## Compatibility constraints

- keep all release metadata at `0.15.4` until the later atomic version sweep;
- preserve existing command identifiers and AI Console behavior;
- preserve the configured `sona.cli.pythonPath` setting;
- use the workspace `.venv` only when the interpreter setting was not
  explicitly configured;
- keep the CLI namespace `sona proof` while all UI naming uses **Proof Mode**;
- do not add TypeScript receipt verification or change schema-1; and
- do not require Guardian for ordinary Proof Mode execution.

## Implementation order

1. centralize safe Python interpreter selection for LSP and CLI commands;
2. add a pure normalized Proof Mode display model with malformed-output tests;
3. add the tree provider and explicit idle/running/valid/invalid states;
4. wire CLI-backed actions and trusted-workspace checks;
5. contribute the view, commands, icons, and menus without changing extension
   version metadata;
6. update extension smoke coverage and user documentation;
7. run TypeScript, extension smoke, npm audit, focused Python compatibility,
   archive inspection, and a fresh external-stage VSIX build.

## Deferred

Automatic receipt discovery, file watching, receipt diffing, cross-workspace
history, TypeScript verification, signatures, remote verification, visual
policy editing, automatic capability prompts, and a broader extension redesign
remain outside this phase.

## Implementation result

The extension now provides the Proof Mode Explorer and CLI-backed run, verify,
inspect, open, refresh, and Guardian explanation actions. Verification remains
owned by the shared Sona CLI; TypeScript only validates and displays normalized
results. Interpreter selection is shared by CLI and LSP launches, trusted
workspace checks protect execution and review, and safe-path Python startup
avoids workspace `PYTHONPATH` injection. Compilation, extension smoke tests,
the 12-member VSIX audit, and the production dependency audit pass with zero
reported vulnerabilities.
