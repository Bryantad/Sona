# Sona 0.15.5 Proof Mode Effect Vocabulary Plan

Release theme: Sona 0.15.5 - Trusted Developer Workflow

Status: implemented and validated

## Current observation architecture

Native Core owns effect observation. `sona-vm` records a sequence, low-level
scope, low-level operation, outcome, and optional execution-local target
fingerprint while Proof Mode observation is enabled. `sona-cli` serializes those
records into `sona.native-proof.schema-1`. The Python `sona.proof` verifier
checks sequence continuity, non-empty scope and operation, known outcomes, and
redacted target syntax.

The current producer observes:

- every exported filesystem call;
- direct `print`, explicit stdout/stderr writes, console flush, and stdin read;
- HTTP attempts, which are denied or unavailable because Native HTTP transport
  is not implemented.

The current producer does not record clock/date reads, sleep, pseudorandom
reads, or random seeding even though those calls cross the same Native host
boundary. It also exposes low-level implementation names such as
`filesystem.fs.read_text`, which are not a stable third-party vocabulary.

Output hashes remain broader than console effect records: they include every
byte emitted through the VM and the CLI-rendered program diagnostic. For
example, an stdin prompt contributes to stdout identity but currently has no
separate stdout-write effect. An effect list is therefore an observation log,
not a proof that unlisted activity was impossible.

## Compatibility constraints

The frozen schema identifier remains `sona.native-proof.schema-1`. Existing
effect records require:

- `sequence`
- `scope`
- `operation`
- `outcome`
- optional `target`

The current verifier already tolerates additional effect-object members. New
receipts may therefore add normalized members inside the existing effect object
without changing core receipt fields or reinterpreting the existing low-level
members. Existing 0.15.4 receipt bytes, hashes, and shared vectors remain
unchanged.

The backward-compatible extension is:

```json
{
  "sequence": 1,
  "effect": "FS.READ",
  "support": "SUPPORTED",
  "scope": "filesystem",
  "operation": "fs.read_text",
  "outcome": "allowed",
  "target": "hmac-sha256:..."
}
```

For a recognized legacy record without `effect` and `support`, verification
derives the normalized pair in its returned result but never rewrites or
re-seals the receipt. If either normalized member is explicitly present, both
must be present and must match the registered low-level mapping. Unknown legacy
operations remain structurally compatible but receive no invented semantic
classification.

## Vocabulary contract

Support status describes Native Core's observation coverage for the normalized
class, independently of whether a particular attempt was allowed, denied,
failed, or unavailable.

| Status | Meaning |
| --- | --- |
| `SUPPORTED` | The listed Native host boundary is instrumented and this operation class is emitted for each invocation. |
| `PARTIAL` | The class is emitted, but known sub-effects or distinctions are not represented separately. |
| `UNOBSERVED` | The runtime operation may occur, but this release emits no record for it. This status belongs in the registry, not a fabricated receipt event. |
| `UNAVAILABLE` | The API boundary is observed, but the underlying Native operation is intentionally unavailable. |

Initial normalized identifiers and mappings:

| Identifier | Low-level operations | Status | Boundary notes |
| --- | --- | --- | --- |
| `FS.READ` | `fs.read_text`, metadata predicates, copy source | `SUPPORTED` for content/copy source; `PARTIAL` for metadata predicates | No raw path is stored. |
| `FS.WRITE` | `fs.write_text`, copy destination | `PARTIAL` | Implicit create/truncate/overwrite is not split into additional events. |
| `FS.APPEND` | `fs.append_text` | `SUPPORTED` | Records the append attempt, not content. |
| `FS.CREATE` | `fs.create_dir` | `SUPPORTED` | Covers explicit directory creation only. |
| `FS.DELETE` | `fs.remove` | `SUPPORTED` | File versus directory removal is not disclosed. |
| `FS.RENAME` | rename source and destination | `SUPPORTED` | Two ordered target records retain low-level source/destination roles. |
| `FS.LIST` | `fs.list_dir` | `SUPPORTED` | Directory entries are not stored. |
| `STDIN.READ` | `stdin.read` | `SUPPORTED` | Input value and prompt are omitted. |
| `STDOUT.WRITE` | `print`, `io.write_stdout` | `PARTIAL` | Stdin prompts and CLI diagnostics are represented only by output hashes. |
| `STDERR.WRITE` | `io.write_stderr` | `PARTIAL` | CLI-rendered diagnostics are represented only by the stderr hash. |
| `CONSOLE.FLUSH` | `io.flush` | `PARTIAL` | The existing call flushes both streams as one operation. |
| `NET.REQUEST` | `http.get/post/put/patch/delete` | `UNAVAILABLE` | Attempts are observed; Native HTTP transport remains absent. |
| `NET.CONNECT` | none | `UNOBSERVED` | Native Core exposes no independently observed connect boundary. |
| `CLOCK.READ` | `date.today`, `time.now`, `time.timestamp`, `time.monotonic` | `SUPPORTED` after this slice | Returned values are not stored. |
| `CLOCK.SLEEP` | `time.sleep` | `SUPPORTED` after this slice | Duration values are not stored. |
| `RANDOM.READ` | `random.float/integer/choice/shuffle` | `SUPPORTED` after this slice | Generated values are not stored. |
| `RANDOM.SEED` | `random.seed` | `SUPPORTED` after this slice | Seed values are not stored. |

`AGENT.ACTION` is not part of this vocabulary. It is a higher-level semantic
claim, not a currently observed Native host operation. A later AI-automation
phase must decide whether it is application metadata or can be grounded in a
real runtime boundary.

## Verification and presentation

The shared Python verifier owns schema validation for the normalized fields.
Guardian continues to consume that verifier and adds no effect-validation
logic. Human verification and inspection views prefer the normalized
identifier and show support status; low-level operation remains available in
JSON results for debugging and compatibility.

## Threat and claim boundary

- An emitted record means the instrumented Native Core boundary observed an
  attempt with the recorded outcome.
- Absence of a record means only that no matching event was observed by this
  instrumentation.
- `UNOBSERVED` never means impossible or denied.
- Target fingerprints are execution-local and do not authenticate the target.
- Output hashes identify bytes but do not imply every byte has a corresponding
  semantic effect record.
- Effect records do not observe operating-system activity outside Native Core,
  Python compatibility execution, child processes, external agents, or host
  compromise.

## Implementation order

1. Add the deterministic low-level-to-normalized mapping to Rust and Python.
2. Emit optional `effect` and `support` fields from new Native receipts.
3. Instrument clock and pseudorandom host calls without recording returned or
   input values.
4. Infer normalized fields for recognized legacy receipts and validate explicit
   normalized fields strictly.
5. Update human verification/inspection output.
6. Add mapping, legacy, mismatch, privacy, and real round-trip tests.
7. Update schema, effects, compatibility, and threat-model documentation.
8. Run the full release gates without modifying version metadata.

## Implementation result

This slice is implemented without changing schema ID, Sona syntax, or release
version metadata.

- Rust emits paired `effect` and `support` fields for all registered observed
  operations while retaining low-level evidence.
- Clock and pseudorandom host boundaries are now observed without recording
  arguments, seeds, or returned values.
- Python verification infers registered classifications for legacy receipts,
  validates explicit mappings, and leaves unknown legacy operations
  unclassified.
- The frozen Native 0.15.4 receipt and original schema-1 interoperability
  vectors remain accepted and unchanged.
- The shared vocabulary is locked by
  `tests/proof/vectors/effect-vocabulary.json` in both implementations.
