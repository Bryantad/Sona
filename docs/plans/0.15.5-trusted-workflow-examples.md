# Sona 0.15.5 Trusted Workflow Examples

Status: implemented and validated

This Phase 10 slice adds four small, repository-owned workflows that expose
what Sona can demonstrate today without implying a stronger trust boundary.

## Current example architecture

The root `examples/` suite is a flat Python-compatible language tour run by
`tools/run_examples.py`. Proof Mode and Guardian have complete command guides,
but no compact task-oriented examples. Native HTTP is intentionally
unavailable, so a network example cannot honestly produce a Native Proof Mode
receipt in schema 1.

## Planned examples

1. **AI action receipt:** treat an external AI proposal as untrusted input,
   then execute a fixed Native Sona tool that reads the proposal and writes a
   controlled local result. The receipt records only the selected program's
   instrumented read/write/output effects. It does not prove AI identity,
   authorship, model behavior, or request causality.
2. **Auditable calculation:** execute a deterministic invoice-total program
   with no filesystem or network grant and preserve its source, output hash,
   execution result, and receipt identity. This is execution evidence, not a
   financial-compliance claim.
3. **Service/API workflow:** call a repository-provided loopback HTTP fixture
   through Python compatibility mode. This example will state that it cannot
   create Native Proof Mode evidence until Native HTTP exists; no fallback or
   network proof will be implied.
4. **Deployment evidence:** copy a fixed example artifact into a local staging
   destination through Native Core. Application version, example source
   revision, artifact digest, and environment label remain declared metadata
   embedded in the preserved program; the receipt records execution,
   program/output identities, capability decisions, and observed filesystem
   boundaries.

## Layout and validation

The workflows will live below `examples/trusted-workflows/`, each with a short
README and the smallest required fixtures. A focused pytest suite will:

- run Native examples with the current Native Core binary when one is supplied;
- otherwise validate their syntax through the Python coordinator;
- execute the service example against a loopback-only test server;
- verify that example documentation names unsupported and metadata-only claims;
- verify committed artifact identity and expected program output; and
- ensure every Native receipt command uses a new destination and the shared
  `sona proof verify` / `inspect` surfaces.

These examples do not add syntax, an agent framework, package registry,
deployment command, Native HTTP transport, signatures, or remote attestation.

## Implementation result

All four workflows are now present below `examples/trusted-workflows/` and are
linked from the example and documentation indexes. Focused Python validation
passes with `7 passed`; the service workflow made a real loopback HTTP request
through the Python-hosted standard library.

The three Native-capable programs were also executed with a Native Core binary
built from this worktree. Each generated a schema-1 receipt accepted by the
shared verifier with `engine: native` and `fallback_used: false`. The controlled
proposal example recorded three effects, the calculation recorded five, and
the local deployment step recorded seven. Both Guardian-bound examples were
accepted by Guardian verification after receipt verification.
