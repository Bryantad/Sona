# Proof Mode and Trusted Automation

Proof Mode can provide runtime evidence for software selected or generated by
an AI workflow. It does not currently prove that an AI request caused an
execution or that a model performed a semantic action.

## Current evidence classes

| Record | Current meaning | Proof Mode evidence? |
| --- | --- | --- |
| Developer-intelligence task record | Redacted application metadata about a provider task, hashes, proposals, and governance | No |
| Governance decision or audit entry | A local provider/task policy decision | No |
| Guardian policy binding | The capability policy and baseline associated with a Native execution | Only when verified inside a bound Proof Mode receipt |
| Proof Mode capability/effect record | A fact observed at an instrumented Native Core boundary | Yes, within schema-1 limits |
| Guardian AI review | Advisory interpretation of already verified redacted facts | No; it adds no trust |

These classes must not be collapsed into one generic “AI audit receipt.” A
model response and a task-record hash do not establish runtime behavior.

## Supported workflow

The honest 0.15.6 workflow is:

```text
AI proposes source or an intended action
        ↓
human or application selects the exact Sona program
        ↓
Guardian constrains supported Native capabilities
        ↓
Native Core executes with Proof Mode
        ↓
Proof Mode records runtime capabilities and observed effects
        ↓
Proof Mode and Guardian verification
        ↓
optional advisory AI explanation of verified facts
```

Proof Mode identifies the exact source or source-backed container that ran. It
does not identify who or what authored that source, why it was selected, or
which earlier AI request led to it.

## Advisory review packet

`sona guardian proof review` verifies the receipt and Guardian binding before
provider routing. The canonical review packet includes:

- receipt identity and verification status;
- execution status and exit code;
- program kind and SHA-256 identity;
- Sona and Native Core identity, including no-Python and no-fallback flags;
- granted capabilities;
- stdout/stderr identities and byte counts;
- normalized effect identifiers, support states, and outcomes;
- the redacted Guardian anchor and local-attestation status; and
- an explicit observation boundary.

Effect target fingerprints are omitted from provider input. Source, raw paths,
output bodies, stdin values, environment values, credentials, and policy
contents are also omitted. `review_input_hash` identifies the exact canonical
packet supplied to the reviewer.

The observation boundary is:

```json
{
  "effect_source": "instrumented-native-host-boundaries",
  "agent_action": "not-represented",
  "ai_request_causality": "not-established"
}
```

Provider text remains advisory even when it accurately summarizes the packet.

## Why `AGENT.ACTION` is deferred

`AGENT.ACTION` is not a registered Proof Mode effect. Native Core has no
distinct agent-action boundary, and current AI/provider execution occurs in
the Python developer-intelligence layer. Emitting `AGENT.ACTION` would restate
application or model metadata rather than runtime observation.

Real tool behavior is represented by the low-level effects Proof Mode can
observe, such as `FS.READ`, `FS.WRITE`, and `STDOUT.WRITE`. Those records do not
establish that an AI requested or caused the behavior.

A future semantic association requires a runner-owned action-request identity,
an explicit binding to one Proof Mode execution and its ordered low-level
effects, and an outcome derived from runtime facts. It must preserve the
low-level records and use a separately reviewed schema or compatible extension.

## Trust boundary

Current Proof Mode provides local self-consistent execution evidence, not
authenticated AI identity, model identity, prompt provenance, request-to-action
causality, signer identity, or remote attestation. Guardian policy and advisory
review do not change those limits.
