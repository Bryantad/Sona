## Inspection before behavior changes

- `sona/cli.py` resolves `SONA_NATIVE_BINARY` before `PATH`'s `sona-native` and
  checks for recursive delegation. It currently launches `proof` without a
  version preflight. A stale executable can therefore produce an older receipt
  even when the coordinating Python CLI is newer.
- `native/crates/sona-cli/src/main.rs` provides a non-executing `--version`
  command with the exact `Sona native <version>` output shape. It is suitable
  for a version compatibility check, but cannot authenticate an executable.
- `sona/stdlib/MANIFEST.json` marks `io.read_file` and `io.write_file` as MOVE,
  recommending nonexistent `fs.read_file` and `fs.write_file`. The actual
  exported functions are `fs.read_text` and `fs.write_text`.
- Canonical Python diagnostics are in
  `sona/developer_intelligence/diagnostics.py`; the parser and LSP share
  `analyze_frontend`. Python runtime exceptions have a separate diagnostic
  adapter surface in `sona/errors.py`.
- Python undefined-name failures use `SONA-RUNTIME-003`; Native Core uses
  `SONA-NATIVE-RUNTIME-003`. The roadmap's `SONA-NAME-001` illustration is not
  an implemented identifier and must not be advertised as one.
- Guardian's infrastructure actually uses `SONA-GUARD-001` for unavailable
  roots, `002` for configuration, and `004` for trusted state. Ordinary drift
  is a structured status. The older registry's `guardian_drift` name must not
  be used to misdescribe current infrastructure errors.
- Sona Guide must not import the existing optional AI service to explain a
  diagnostic. That service can resolve providers and write task receipts.

## First-slice decisions

1. Require an exact CLI/Native version match before delegated Proof execution,
   including when `SONA_NATIVE_BINARY` is explicit. Older, newer, malformed,
   missing, or timed-out version output cannot launch the program. Offline
   verification of valid historical receipts remains independent of discovery.
2. Bound version probing by time and output size. Do not echo arbitrary probe
   stderr or host exceptions. Report whether selection came from the explicit
   setting or `PATH`; remediation must not claim the version probe proves
   binary authenticity.
3. Own launch diagnostics in `SONA-NATIVE-LAUNCH-*`; these failures occur before
   the producer and must not be reclassified as receipt verification failures.
4. Implement reference lookup as `sona why <id> [--mode guided|balanced|expert]
   [--style simple|visual|technical] [--json]`. Reference explanations are not
   claims that a program ran or a receipt was verified.
5. Store deterministic sections and concept IDs in one Guide catalog. Retain
   canonical diagnostic payloads when explaining a supplied diagnostic. Text
   density must not change the compiler's fact payload.
6. Keep the initial catalog to five topics: names, delimiters, filesystem
   permission, receipt integrity, and Guardian readiness. Multiple existing
   IDs may share a topic without being renamed.

## Phase 4 inspection and implementation order

The LSP has shared frontend diagnostics, completion, hover, and navigation. It
does not emit runtime undefined-name failures during static checking. A runtime
quick fix therefore requires the original Sona diagnostic in request context;
Guide must not execute a program to manufacture editor diagnostics.

The extension already owns a language client and delegates trust operations to
Python. Its existing Explain Code command uses optional AI. New offline Explain
Diagnostic and Explain Selection commands will have distinct identifiers.

Implementation order:

1. Expose the shared deterministic fix rules as versioned LSP document edits.
   Preserve zero-width insertions and UTF-16 ranges. Disable edits for clients
   without versioned-edit support; do not label metadata alone as enforcement.
2. Add one bounded, read-only Guide JSON request service, available through
   CLI stdin and the LSP. Preserve canonical payloads and explicitly report
   unsupported explanations. Selection explanations describe parser-recognized
   constructs and never claim a program ran.
3. Wire the extension's explanation commands and presentation preferences to
   that service. Use native editor surfaces for keyboard/theme accessibility,
   an optional first-run mode choice, and no provider dependency.
4. Use the same concept catalog to enrich completion/hover. Test transport parity,
   stale edits, recomputation, malformed inputs, and complete-output preservation.

The first protocol smoke passed, but review found that diagnostic-range widening
could turn an import insertion into a one-character replacement. Exact edit
ranges now preserve insertions. Actions use `documentChanges` with the open
document version; the LSP client must reject a mismatched version. The shared
fix payload retains expected-original text for richer preview clients. Three
protocol checks now exercise actual edit application, CRLF/UTF-16 conversion,
version rejection, post-change recomputation, closed documents, and clients
without versioned-edit support.

## Phase 5 inspection and implementation plan (before code)

The existing `tools/run_examples.py` executes nine official onboarding sources
through the real interpreter, but imports checkout-only `run_sona` and removes
`.sona` directories in the original examples tree. Installed wheels exclude
examples; there is no `sona examples` or top-level `sona learn` command. Four
trusted-workflow examples have separate executable tests, including a loopback
HTTP fixture that is explicitly Python-only. Those tests must remain in CI.

Implementation order and contracts:

1. Keep existing `examples/` files authoritative and unchanged. Add a schema-1
   manifest under `sona/data/` identifying curated sources, required fixture
   assets, runtime, lesson concept, and exact deterministic output checks.
   A setuptools build step copies only declared assets into wheel resources;
   sdists contain the same source assets so a wheel can be rebuilt offline.
   No hand-maintained second copy of program text is introduced.
2. Add read-only catalog/resource loading and an execution runner outside
   `sona/guide/`. `sona examples` lists available examples; `run <name>` executes
   only a named, shipped program in a new temporary directory, with a timeout
   and bounded output. This is workspace isolation, not an OS security sandbox.
   Ordinary examples explicitly use the real Python compatibility engine;
   receipts require the real, version-checked Native engine with no fallback.
3. Replace the old runner's original-tree cleanup with the same manifest-driven
   execution contract. Preserve and run all nine existing official examples,
   plus the existing trusted-workflow tests. Add conditions, loops, collections,
   files, Guardian, and Proof Mode learning examples as needed.
4. Add `sona learn` only after execution checks exist. Lesson descriptions reuse
   the Guide concept catalog. `learn run <topic>` is an explicit practice action;
   successful checks record only concept familiarity in schema-1
   `.sona/learning.json`. They never assert mastery or downgrade `comfortable`.
   `--no-profile` disables persistence. Listing/explanation is read-only.
   A correctly denied Guardian operation is a passed lesson check, while the
   receipt must still truthfully say execution failed.
5. Designate documentation samples executable with explicit manifest references
   and test their source against the authoritative asset. Add matching-host CI
   gates for the full curated catalog, trusted workflows, docs, packaged wheel,
   and sdist-to-wheel reconstruction. Do not claim these remote gates ran locally.

Examples/learning JSON uses schema-versioned results. Source text, output, and
temporary paths are not learning-profile fields. Unknown names, malformed
manifests, unavailable assets/runtimes, failed checks, and time/output limits
must fail clearly; there is no simulated success or hidden compatibility
fallback. Versions, Git history, and publication remain unchanged.

## Verified-fact presentation audit and plan (before code)

`sona.proof.inspect_receipt` already returns the shared verifier's normalized
facts or its original invalid-receipt diagnostic. `guardian_check` returns
policy source, drift, capability decisions, legacy-baseline state, readiness,
and an explicit `policy_enforced` flag. Readiness alone does not establish
policy enforcement; receipt `guardian_bound` alone does not verify a baseline.
The existing plain renderers have no Guide mode selection. The post-learning
baseline is 765 passing tests and three privilege-dependent skips.

The next slice extends GuideRequest with an exclusive structured-fact variant
without changing existing diagnostic JSON. A pure Guide renderer preserves
the complete provider facts in every mode, puts hashes behind technical detail,
and keeps assurance warnings visible even in Expert mode. A coordinator outside
Guide calls the existing verifier/checker for new read-only `sona guide proof`
and `sona guide guardian` commands. It must never accept caller-asserted
`status: valid` as a substitute for verification. The editor can later consume
this same CLI JSON; no TypeScript verifier or prose knowledge is introduced.

Tests will cover the frozen 0.15.4 receipt, invalid/corrupted evidence, all three
modes, real Guardian uninitialized/ready/drift states, original fact preservation,
and no project/profile writes. Legacy binding, readiness, policy enforcement,
receipt integrity, and execution success remain distinct facts. No repair,
attestation, initialization, execution, or capability grant is performed by
these explanation commands.

## Runtime-diagnostic handoff audit

The editor's current Run command receives stdout/stderr text only. The Python
run handler catches the canonical runtime exception and renders it, but exposes
no JSON run result. Parsing that formatted text in TypeScript would lose
diagnostic ownership and precise ranges. The first handoff step will therefore
add opt-in `sona run <file> --json`: actual execution through the existing run
handler, captured program streams, original structured runtime diagnostics,
and the exact decoded source identity used for execution. Ordinary run output
and semantics remain unchanged. Unknown/internal failures must not be invented
as undefined-name diagnostics. Editor publication must later require the same
source identity and document version, then clear findings on changes; LSP
analysis must remain non-executing.

### Runtime-diagnostic implementation and evidence

Added opt-in `sona run <file> --json` as a development transport for real run
results. It delegates to the existing run handler, captures bounded stdout and
stderr prefixes, preserves the original exit code, records decoded source
identity as `utf8-decoded-text-lf`, and includes canonical runtime diagnostics
only when the underlying handler produced them. Ordinary `sona run` output is
unchanged. Missing files and internal failures do not invent an undefined-name
diagnostic.

The transport marks embedded `@check_types` extraction as
`source_mapping: transformed`; consumers must not treat those locations as direct
editor-buffer edits. The transport is not Proof Mode evidence, not a sandbox,
and does not add a new execution timeout. It bounds serialized output, but it
does not prevent the executed program from running arbitrary behavior already
allowed by normal `sona run`.

Updated the VS Code Run command to require a trusted workspace, save the active
Sona document, call the structured run transport, show captured program output,
and publish runtime diagnostics only when all of these remain true:

- the run packet is schema-1 `command: run`;
- `source_mapping` is `original`;
- the packet source hash matches the saved editor text normalized the same way
  as the CLI transport; and
- the editor document version did not change while the command was running.

Published diagnostics keep `source: "sona"`, the stable diagnostic code, and the
full canonical diagnostic payload in `data`, so the existing Guide explanation
