# Sona 0.15.5 Implementation Report

Release theme: **Trusted Developer Workflow**

This report records the implemented 0.15.5 architecture and the local release
candidate validation boundary. It does not claim publication, a clean tagged
source state, or validation on operating systems that were not exercised.

## Implemented architecture

- `sona proof verify` and `sona proof inspect` use one Python verifier for
  canonical parsing, schema validation, self-hash integrity, field contracts,
  runtime/engine identity, capability/effect records, and Guardian binding.
- Native Core remains the only schema-1 receipt-producing engine. It records
  no Python participation and rejects fallback.
- New receipts can carry an optional, validated runtime-identity extension
  containing the running Native binary hash/size and a build-supplied source
  revision. Frozen 0.15.4 receipts and vectors remain unchanged.
- Guardian policy supplies capability decisions before Native execution;
  instrumented host effects become receipt evidence; Guardian can then check
  the local baseline/policy binding.
- AI review consumes redacted, verified facts only as advisory output and
  cannot create, modify, verify, or strengthen evidence.
- The VS Code Proof Mode Explorer delegates verification and inspection to the
  installed Sona CLI.
- `sona pkg` and `spm` delegate to the same local-only, atomic SPM engine.

## Compatibility decisions

- Schema-1 required fields and canonicalization are unchanged.
- Runtime identity is optional so 0.15.4 receipts remain verifiable.
- No Sona syntax was changed.
- Existing Proof Mode and Guardian commands remain available.
- Native HTTP, remote attestation, signatures, PKI, package registries, LSP
  rename/references, and deployment orchestration remain out of scope.

## Validation boundary

The final local gate covers the complete Python suite on Python 3.12, the Rust
workspace tests and strict Clippy gate, Native standalone Proof Mode checks,
LSP/SPM/onboarding/example regressions, extension compilation and smoke tests,
production dependency audit, wheel/sdist metadata and archive inspection,
VSIX member inspection, release metadata validation, standard-library catalog
consistency, and `git diff --check`.

Observed local results on Windows x86-64 with Python 3.12.13, Rust 1.94.0, and
Node 20.19.5:

- Python: 559 passed, 3 skipped, and 2 dependency deprecation warnings. The
  skips require Windows symlink privileges unavailable on this host.
- Rust: `cargo fmt --check` passed, strict Clippy passed, and all 39 workspace
  tests passed.
- VS Code extension: compile/bundle and smoke tests passed; the production
  dependency audit reported 0 vulnerabilities.
- Ruff passed for the 0.15.5-owned Python modules and focused test surfaces.
  The broader legacy repository is not represented as lint-clean.
- Python artifacts: wheel and source-distribution clean installs, `pip check`,
  `twine check`, metadata inspection, and archive inspection passed.
- Portable artifacts: the wheel has 330 members, the source distribution 359,
  and the VSIX 12; all passed the versioned release inspector.
- Windows machine verification: the fresh 0.15.5 wheel, Native execution,
  Proof Mode receipt, Guardian baseline/binding, local attestation, and
  deterministic review passed together.
- Packaged runtime identity: the receipt's Native binary SHA-256 exactly matched
  the extracted executable.

The Windows source-mode packager passed Rust formatting, strict Clippy, all 39
workspace tests, release compilation, execution and Proof Mode smoke checks,
single-member archive inspection, and PE dependency inspection through the
Rust 1.94.0 `llvm-readobj` component. The report records `build.mode: source`,
`target_mode: host-default`, `dependency_inspection.status: pass`, and no Python
DLL dependency. Windows Application Control briefly denied one newly generated
test executable on its first launch; running that unchanged harness after host
scanning completed and rerunning the complete packager passed.

Because the working tree is not committed, the local source candidate
intentionally omits the optional receipt `source_revision`; its runtime identity
still records and verifies the exact Native executable SHA-256. A clean-commit
CI rebuild will populate `source_revision` with the commit actually used for
the build.

Matching Linux and macOS release runners remain required before publishing
their Native archives. A local dirty-worktree candidate is useful for manual
testing but is not a final clean-commit release certification.

## Known risks

- Most broad application workloads still use the Python compatibility engine;
  Native Proof Mode applies only to the bounded Native surface.
- Native HTTP is intentionally unavailable.
- A receipt self-hash provides integrity consistency, not authentication.
- Build-supplied source revision is correlation metadata, not authenticated
  source provenance.
- Guardian attestation is a local audit record, not cryptographic attestation.
- Cross-platform Native compatibility is not established until matching-host
  build and test jobs pass.
- A repository-wide Ruff audit reports 942 legacy findings. This release
  certifies its scoped 0.15.5 lint surface and does not claim a broad style
  cleanup.
